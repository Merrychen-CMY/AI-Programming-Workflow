# 用户确认边界，L1管理执行额度

从3.3.0起，新插件任务默认在开工草案中设置`adaptive_limits: true`。用户确认目标、硬约束与AC、权限范围、资源总上限和最终截止时间；L1自动制定并调整细粒度执行参数，最后报告调整理由、实际消耗和结果。模板数值仅是待确认示例，不是授权，也不代表所有项目都应使用同一额度。

原始输入与开工确认保持原样。`resources.json`追加保存当前额度、授权变更、调整理由、历史和暂停点；已有API账本、实现次数、失败记录、事实和审核记录继续累计。原始委托不被新版本覆盖。摘要链用于发现本地意外改动，不是签名审批服务或同账户进程间的安全隔离。

## 两层资源边界

| 项目 | 用户确认的边界 | L1的权限 |
| --- | --- | --- |
| 目标、硬约束、AC | 原始输入及用户明确批准的后续变更 | 在已授权含义内细化；改变目标或标准必须先申请 |
| 文件范围 | 项目内允许路径 | 在范围内分工；扩大范围须用户批准并重审计划 |
| 资源与时间 | 整个任务的次数上限、每操作最大超时/输出、总经过时长、绝对截止时间 | 在各项上限内分配和调整当前额度；不改累计消耗 |
| 实现和验证方案 | 已批准需求及独立验证要求 | L1组织重新审查受影响基线，DOT调度，L4独立重验 |
| 设备、网络、外部交付 | 用户具体授权及实际执行器能力 | 不能通过文字或预算调参获得未实现的权限；本运行器仍不执行外部交付 |
| 历史、UNKNOWN、最终报告 | 原始事实保留 | 不能删除历史、将批准当作操作已停止的证据、直接撤销最终失败 |

用户不需要逐项设计重试策略或填写JSON。L1根据任务规模准备开工建议，并用清楚的单位说明上限；用户一次确认整体边界。当前额度耗尽后，先暂停派工，由L1评估；不是立即生成最终失败。

## 参数及真实计数单位

`limits`在开工委托中是用户上限，在`l1_adjust_limits`中是L1当前分配。两者都要求以下九个字段；所有次数都是累计上限，不是“再增加几次”。计划中的`budgets`记录制定计划时的分配，执行时以当前分配为准，不能沿用旧大额预算越界。

| 字段 | 单位与含义 |
| --- | --- |
| `implementation_attempts` | 全任务L3派工次数，初次实现和修复共用；已完成任务不会因增加额度自动重做 |
| `same_root_cause_attempts` | 同一具体根因累计失败阈值；达到当前阈值，下一次重试前进入L1评估 |
| `infrastructure_retries` | 全任务设施/证据恢复的额外重试次数，可以为0 |
| `timeout_seconds` | 每次工作会话/审核/检查的最大秒数，并受剩余总时长和截止时间约束 |
| `l1_reviews` | 需求和计划的独立审核累计次数，包括拒绝的审核 |
| `revisions` | 已初始化基线修订与事实补充共用的累计次数，可以为0；不是每个阶段重新计数 |
| `api_calls` | DOT API累计请求次数，包括已发出后失败或结果未知的请求；不含配置页的独立探测 |
| `api_max_output_tokens` | 单次DOT API输出token上限；不是全任务token总额 |
| `wall_time_seconds` | 从任务首次建立API/审核账本起的经过秒数；新流程在首次需求独立审核前开始计时，包含暂停和等待，调整不重置起点 |

此外还有`expires_at`绝对截止时间，较早达到的时间边界优先。API等待默认120秒，L1可通过`l1_review_api`调整，实际等待受当前单次操作额度、剩余总时长和截止时间共同约束；不是固定120秒上限。桥接进程4小时、输入大小及原生确认界面大小等实现限制仍存在。本版没有跨L1、DOT和Codex的统一货币/总token硬限额；报告保留API返回的用量，未知部分不能记为0费用。若用户要求精确金额硬封顶，必须先有可核实的账户侧或其他计量控制，不能把调用次数等同于费用保证。

## 正常调用与额度评估

1. 配置模型和密钥 → 检查基础环境 → 沟通九项原始需求 → 复核项目条件 → 用户集中确认开工。新草案启用动态管理。
2. L1调用`l1_adjust_limits(proposal_json)`分配初始额度，格式见[额度模板](../../templates/resource-allocation.example.json)。这一步是本地记录，不调用GPT、不派工。
3. `l1_prepare_requirements` → `l1_approve(kind=requirements)` → `dot_plan` → `dot_initialize` → `l1_approve(kind=plan)` → `dot_run`。先独立审核并批准需求，再规划；初始化承接已有需求审核和累计消耗。
4. 返回`BUDGET_REVIEW_PENDING`时，读取`resources.budget_review`和`runtime_state`：当前额度、用户上限、已用次数、待执行任务、失败证据。DOT说明剩余工作、根因及建议；L1记录理由、证据、预期收益、剩余工作和策略。
5. 若增加额度有明确收益且仍在授权内，调用`l1_adjust_limits`保存完整新额度。也可在实现额度暂停时由L1调用`dot_plan`合理合并未完成派工，保留全部需求、AC和独立验证；新草案必须满足累计已用＋剩余派工不超过当前额度，才追加记录并解除这项暂停。规划本身仍受API、时间、需求审批及未决授权门禁限制。已有运行任务须`l1_revise`并独立重审新计划；不能拿新草案继续执行旧计划。无效或越界调整正常拒绝；不能只写相同额度消除未解决的检查。两种路径均不自动派工。
6. 仅调整数值不要求重审产品基线；若方案、需求、测试语义或文件范围变化，则重新规划、独立审核受影响基线，再按候选规则验证。已完成的实现任务保持完成；实现缺陷仍先经L2分析再派L3。
7. 无法核实操作结果时先暂停并保留未决状态，由L2调查、L1协调。只有L1明确评估无可行方案、原生用户要求停止或全任务限制已确认无法调整，才提交完整非成功最终报告；缺资料、当前额度不足和结果尚未核实本身都不是结案依据。不能为避免失败而无限加量。

暂停前尚未完成的根因分析会保留为`pending_triage`；恢复时先继续分析。已经诊断的修复和设施重试保留待办，不因暂停丢失，也不重复记同一诊断。纯额度暂停返回`COMPLETED_BUDGET_REVIEW`，原生插件仅清除此轮已完成的在途标记；真实UNKNOWN继续阻止重放。

## 超出边界时申请用户授权

L1调用`l1_request_authorization(proposal_json)`保存具体差异，格式见[追加授权模板](../../templates/authorization-request.example.json)，随后调用无参数的`workflow_review_authorization`。原生界面展示变化前后值、理由、证据、预期收益、风险、累计消耗及恢复方案。用户明确选择批准或拒绝，跳过/取消继续等待；模型不能提交`approved`或伪造用户身份。

本版可批准的字段为`limits`、`expires_at`、`allowed_paths`、`hard_constraints`和`authorized_context`（明确的新目标/AC文本）。必须完整、具体，不以“全部放开”代替边界。批准绑定申请摘要、当前任务状态和当前授权；审核期间内容或状态变化则拒绝旧回执。减少上限不得低于已用值，现有分配也会受新上限约束。

纯资源或截止时间授权后，L1仍需调整实际额度；不会清零或自动派工。目标/AC/路径/约束变化后必须重新规划，旧批准失效；已初始化任务用`l1_revise`建立新基线，并独立审查后执行。过期任务可申请具体延期，但旧截止时间和经过时长保留。

设备/网络/外部交付权限开关、取消独立验证、删除历史、清除UNKNOWN及撤销最终报告不在上述接口支持范围。用户有意改变这些边界时，L1应说明所需授权和控制器能力缺口；批准本身不能证明操作结果，不能把未做的测试改为通过。本版须保留旧任务和报告，在明确关联历史的新任务或专门核实/实现恢复能力后处理，不能假装接口已经支持。

手动MCP桥可调用两种资源工具，但没有供模型使用的人类批准入口；需要追加授权时使用原生插件承载的任务，不能填一个“用户已批准”字段代替。旧任务未声明`adaptive_limits: true`时保持原行为；不修改旧确认来强制迁移，不自动解锁旧UNKNOWN/最终报告。

## 状态与最终报告

`BUDGET_REVIEW_PENDING`和`AUTHORIZATION_PENDING`是桥层暂停状态，`runtime_state`保留原阶段；恢复后回到该阶段。授权等待期间禁止普通执行工具；仍可查看状态、停止并提交报告。跨越边界的批准先解决暂停和受影响基线，不能直接跳到成功。

最终报告包括原授权、后续用户决定、每次L1调整的前后值/理由/证据/收益判断、累计实际消耗、未完成工作与结果。`resource_governance`保存完整记录，API原始用量在账本中保留。失败或UNKNOWN报告审核不授权重试；不撤销历史报告来继续旧执行。

拒绝测试见`tests/test_resources.py`和`harness/tests/workflow.test.js`：越上限、低于已用、没有实际新增容量、伪造批准、过期或陈旧申请、范围变化沿用旧计划、API/实现/审核/修订/设施额度暂停、诊断恢复、历史篡改及UNKNOWN/最终报告保护。它们是运行器测试，不是产品或HIL验收。

3.6.0的[初始化恢复](initialization-recovery.md)单独核实并审核未提交初始化；普通调参权限不因此扩大。恢复记录纳入状态/报告，原额度与截止时间不变。

3.7.0将API网络等待纳入已有单次操作timeout_seconds上限；API等待值默认120秒，由l1_review_api配置，实际取该值、当前操作额度、剩余总时间和截止时间的最小值。l1_adjust_limits可先在用户上限内调整操作额度；超出总授权仍走原生追加授权。详见[API评估与恢复](api-recovery.md)。

3.11.0的可执行恢复入口与报告门禁见[完整流程与恢复](flow-recovery.md)：新原生任务强制动态额度和需求先审后规划；问题待决使用只读调查和L1恢复决定，真实中断须核实后原生批准；不重开最终报告。
