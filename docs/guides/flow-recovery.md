# 3.11.0：完整主线与问题恢复

本页对应 README 流程图，规定新原生 Harness 任务的实际顺序及恢复入口。L1 仍是唯一用户入口；用户集中确认目标、权限、资源总上限和截止时间，L1 自动管理范围内工作，最终报告由用户审核。华为 C、Doxygen、独立验证及真实证据要求保持有效。

## 从需求到执行

1. 配置模型和密钥 → 检查基础环境 → 沟通原始需求。随后复核项目特有工具链、构建、测试及设备条件；文件存在不能代替真实构建或 HIL。
2. 原生界面集中确认开工摘要。新任务必须采用 `adaptive_limits: true`，由 L1 使用 `l1_adjust_limits` 分配当前额度。
3. L1 完成产品需求与内部 L1-V 验收要求，调用 `l1_prepare_requirements(requirements)` 暂存文本；此步骤不调用 DOT，也不派产品工作。
4. 调用 `l1_approve(kind="requirements")`，由独立只读会话审查。通过后记录 L1 代理批准，绑定需求、原始输入、当前授权范围、补充事实、项目基线及本版规范。审核会话不能是需求作者；调用前预留审核次数，失败也保留。
5. 只有批准有效，才可 `dot_plan(requirements)`。必须传入已批准的同一份文本；需求、事实、范围或项目基线变化须先重新审查需求。
6. `dot_initialize` 固定项目快照并承接真实需求审核记录，进入 `PLAN_PENDING`，不重复需求审核，也不清零已用审核次数和总时长。
7. `l1_approve(kind="plan")` 独立审查详细执行计划。通过后 `dot_run`，运行器分别派发开发、测试和审核会话。
8. 所有失败先交 DOT/L2 分析。满足成功门禁才生成成功证据报告；其他结案必须先经过 L1 的明确评估。两类报告均经 `l1_submit_report` 后，才由 `workflow_review_report` 请求用户审核。

首次需求审查没有详细执行计划，因此核对的是验收义务、测试环境与方案要求。DOT 后续生成可执行的命令、任务依赖及候选验证计划，再经独立计划审查；不得要求第一轮需求审核提供尚未获准生成的详细计划。

## 问题暂停后怎样继续

`DECISION_PENDING` 表示问题等待调查或决策，不代表任务结束。L1 先读取 `dot_status` 与最新问题，再通过 `dot_read_record` 查看已有原始记录。需要继续分析时调用 `dot_investigate(investigation_json)`，内容包含明确的 `question` 和 `evidence` 路径列表；该入口仅分析已有记录，不执行产品代码。

L2 的结果必须提供 `solutions` 或 `investigation_steps`，并分别列出 `missing_information`、`permission_gaps` 和 `recommended_action`。每个方案说明内容、预期收益、验证步骤、资源及权限缺口。证据不足时必须提出调查步骤，不能仅填“未知”或空列表。

| L1 评估结论 | 继续方式 | 保留的保护 |
| --- | --- | --- |
| 已有证据足以修复实现 | `l1_resume_decision` 选择 `repair`，再 `dot_run` | L2 须有完整的授权内方案；审批、项目快照、证据与额度仍需有效；L3 执行修复 |
| 已完成实现，设施或证据问题可恢复 | 选择 `reverify`，再 `dot_run` | 不跳过未完成实现；新候选重新独立验证 |
| 还需分析 | 选择 `continue_investigation`，再 `dot_investigate` | 明确范围和证据，保留所有调查及消耗 |
| 需求或验证基线需改动 | 选择 `revise_baseline`，按修订入口重新审查 | 不改变用户目标或权限；越界先申请授权 |
| 资源不足 | `l1_adjust_limits`，越界则 `l1_request_authorization` → `workflow_review_authorization` | 当前额度、用户总上限、累计消耗分别记录；批准不自动派工 |
| 旧操作结果未核实 | 原生操作恢复流程 | 不自动重放，不直接删除中断标记，不把旧 UNKNOWN 改成 PASS |
| 确实没有可行方案 | L1 提交有真实证据引用的结案评估 | L2 只能建议终止；不能直接生成最终失败 |

`l1_resume_decision` 的 `decision_json` 使用 `action`、`reason`、`evidence` 三个字段。`evidence` 为从 `control/` 起算的真实记录路径。此决定不授予新权限；存在未决进程、未决 API 请求、批准失效或方案权限缺口时，恢复执行会被拒绝。

## 保留已经完成的工作

同一需求、任务定义和依赖未受影响且项目快照仍匹配时，修订保留完成标记，不重新派发同一实现任务。需求、任务或依赖有实质变化时，仅保留能够证明不受影响的部分；项目内容与已记录检查点不符时保守失效受影响工作。记录保留/失效清单及理由，累计实现次数不回退。

候选、审批和验证结果仍按基线变化重新核验；“保留已完成实现”不等于复制旧候选的 PASS。修复生成新候选，独立测试与审核重新执行。

## 真实中断的受控恢复

操作恢复与普通问题调查、API 请求恢复、未提交初始化恢复分别处理。L1 调用 `l1_prepare_recovery(proposal_json)` 准备 `reason`、`analysis`、`resume_plan`、`side_effects` 和 `evidence`；每项证据包含control相对 `path`、实际 `sha256` 和 `description`。随后 `workflow_recover_operation` 原生界面展示绑定当前状态、项目指纹和进程检查的准确方案。只有用户明确批准、旧进程已停止且证据未变化，才归档原中断记录并完成受控状态转换。事务再次中断时只完成已批准的本地写入。

需求首次独立审核也适用此规则：审核结果 UNKNOWN 会保留未决审核，不能自动再次审核；核实后仍保留旧 UNKNOWN 与已用次数，新的审核是新尝试。产品执行 UNKNOWN 不会被需求暂存、额度调整、补充事实或升级直接清除。已生成最终报告的任务不能由恢复入口重开。

## 开工前与开工后的报告

初始化前的 `preflight-report.json` 和初始化后的 `run/final-report.json` 都先由 L1 提交最终判断，再由用户审核。缺少 L1 提交时，用户审核入口拒绝；L1 不能改变原始结果、证据或替用户确认。

非成功结案必须记录考虑过的方案、权限审查、资源评估、终止依据及实际存在的任务证据。声明“用户要求停止”还需要真实原生停止记录；模型自述不是授权。证据路径会核验并绑定摘要，但本机记录仍不是签名审批服务，结构校验也不能证明自然语言分析正确。

用户要求停止时，L1 先调用无模型审批参数的 `workflow_confirm_stop`。入口先暂停新派工和重试，再展示本任务、当前额度和累计用量。明确选择“确认停止”后，原生宿主写入绑定任务与会话的 `control/user-stop.json`；关闭窗口或未答复保持暂停。明确选择“不停止，回到原流程”只撤销尚未确认的停止暂停，其他权限和中断守卫仍有效。已批准而尚未完成的本地恢复/升级事务本身已暂停派工，应先完成那份精确事务，再确认停止，避免互锁。

停止记录不会清除 `active_run`、UNKNOWN、累计用量或原始证据，也不宣称进程已经终止。随后 L1 用 `l1_stop` 提交结构化结案评估，`termination_basis` 为 `user_requested_stop`，证据引用 control 相对的 `user-stop.json`；再提交最终报告供用户审核。不得为了取得停止收据继续产品执行，停止工具本身不会直接生成最终失败报告。实现入口为 `harness/user-stop.js` 与 `runtime/dot_runtime/user_stop.py`。

## 安装与历史兼容

本版新增工具需要安装 **3.11.0 / ABI7 主插件包**。兼容运行包更新不能向 ABI6 宿主凭空添加工具；已确认任务仍固定原运行版本，升级须按原生预检和批准流程完成。已开工旧任务及历史 CLI 模式按原有收据保留，不伪造“需求先批准”的历史；新原生任务强制动态额度及需求先审后规划。升级不是清除 UNKNOWN、撤销最终报告或重置预算的入口。

## 拒绝与回归检查

以下是必须保留的行为，测试结果需单独记录，不因列出清单就视为通过：

| 场景 | 必须观察到的结果 |
| --- | --- |
| 未批准需求就调用 DOT 规划 | 明确拒绝，无本次 API 请求 |
| 作者充当需求审核者、审核会话复用或证据被篡改 | 无有效批准，保留记录 |
| 需求/事实/权限范围/项目指纹变更后沿用旧批准 | 拒绝规划或初始化，要求独立重审 |
| 首次审核后初始化 | 继承真实审核与累计用量，直接进入计划待审 |
| 进入问题待决后继续调查 | 可在原授权内只读分析，不能暗中派产品工作 |
| L2 空方案、证据不足却建议直接修复 | 拒绝执行，继续调查或交 L1 |
| 无关修订或只调整额度 | 已完成实现不无故重派，累计消耗不清零 |
| 基线变化或任务依赖变化 | 受影响标记失效，批准及候选重新核验 |
| 未核实的进程、陈旧恢复预览或伪造用户确认 | 拒绝恢复，不删原标记 |
| 开工前结案但尚无 L1 提交 | 用户报告审核入口拒绝 |
| 新原生任务关闭动态额度 | 开工校验拒绝 |
| 任意自动错误直接请求失败结案 | 暂停并交 L1 评估，不自动生成最终报告 |

单元测试、模拟模型集成、本机真实工具运行、真实 Harness 会话和实际产品/HIL 验收是不同证据层次；不得相互代替。
