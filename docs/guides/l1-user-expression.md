# L1面向用户的需求沟通与报告表达

采用五条表达约束：结论优先、减少套话、保留必要异议、事实不随措辞改变、分层呈现。权威规则为[communication.json](../../policy/communication.json) revision 2中的L1-EXPR-01～05；与[合作沟通约束](l1-dot-communication.md)一起使用。

用户职责保持：与L1沟通原始需求，审核L1提交的最终成功/失败报告。原始需求、硬约束、验收、授权、证据以及华为/Doxygen规范优先于表达偏好。语言可以精简，事实和承诺不能因润色改变；不增加审批、模型调用或用户表格。

## L1如何沟通原始需求

先用简短、可核对的文字复述用户目标、已知参数和硬约束，再提出确实影响方案或验收的关键缺口。优先查已有材料；明确区分用户原话、事实、推断、建议和未知。不要求每句话加标签，也不规定固定问题数量。

主动检查边界、异常场景和相互冲突的要求；建议需要说明理由与影响。不能为便于实现而诱导用户降低目标，不能把建议写成用户已确认的要求。生成[需求文档](../../templates/requirements.md)时保留参数、单位、阈值、版本和规范强度。

原始需求阶段可以澄清关键事实；执行中委托内的需求/计划问题走原L1/DOT回流。当前额度不足先由L1评估并在用户上限内调参；超出目标、权限、总上限或截止时间时按动态资源流程申请具体追加授权。无可行方案或无法核实才提交失败/未完成报告；表达规则本身不增加审批。

## L1如何汇报结论

使用[最终报告模板](../../templates/final-report.md)，先给真实状态及候选/环境范围，再给关键AC及证据、失败/重试概况和累计消耗、未验证项、风险、产物及下一步。完整逐项结果与历史可在可取得的附件中，但影响验收的信息必须在正文清楚披露。

SUCCESS、FAILED、INCOMPLETE、UNKNOWN保留原义；单项测试通过不能变成整体验收成功。DOT原始报告、结构化回执、批准记录和证据不由表达规则重写。L1提交说明不能升级原结果，也不能把“用户已知晓失败”当作通过或重新开工授权。

以下均为虚构示例，不是已执行的产品证据：

- 响应时间要求≤100 ms，实测130 ms：正文明确“未通过该项验收”，同时可以说明已通过的功能；不能改为强调吞吐优势并隐去超时。
- 主机测试通过，但必需板上测试未执行：正文写明缺项及INCOMPLETE，不能用“已验证”代指全环境成功。
- 前两轮失败、第三轮通过：说明最终候选结果，同时保留前两轮原因、重验和累计消耗；详细日志可附后。
- 原始信息同时给出两种电压：指出矛盾并集中澄清，不能默选易实现的一种并写成已确认。
- 工具退出后的真实结果无法核实：明确UNKNOWN与影响；不改成失败后重试或默认成功。

必要措辞可以直接使用“失败”“未达到”“未验证”“风险”“但是”；不做机械词语屏蔽，也不要求全部句子使用肯定语气。

## 接入位置与验证边界

1. L1首次沟通前按[L1.md](../../L1.md)和[Harness指南](l1-harness.md)加载本规则。桥初始化也通过`communication.l1_prompt()`提供五条规则；独立需求/计划审查收到同样的完整性边界。
2. GPT/DOT继续通过`communication.prompt()`使用COMM-01～04及既有执行约束，不加载L1用户表达部分或上游论文规则；开发/测试工具结构不变。
3. 规则与其他沟通策略一起参与批准/候选基线摘要；旧批准不能因规则变更静默复用。更新后重新加载L1资料并初始化桥，运行中任务走既有基线变更流程。
4. 自动检查覆盖策略边界、固定来源/许可、提示作用域、基线失效以及报告证据保全；不把字符串或结构校验称为模型诚实性证明。未进行真实Harness对话对照实验，未证明更省Token或更少轮次。

后续实际对话可检查：关键问题是否遗漏、原始要求是否被改写、验收失败是否在正文明确出现，以及解释是否足以作决定。上述虚构案例可用于人工评估；不是已完成的模型拒绝测试，不增加用户审批门禁。验证记录见[3.0.3](../reports/3.0.3-validation.md)。
