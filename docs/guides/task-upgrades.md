# 已开工任务在原对话升级

ReqPilot 3.5.0提供经原生确认的任务版本迁移。无需重新描述需求、重新开工或清零预算。后台下载新版仍不会擅自迁移已确认任务；是否迁移是单独的版本决定，不重新审批全部产品资料。

## 如何使用

先安装一次reqpilot-3.5.0.tgz，使Harness加载ABI3入口。3.4.x入口不能自行替换自身；按宿主要求重新加载插件。如果原对话仍只有旧入口行为，需由宿主恢复/重新加载原对话，保留其会话ID和任务目录，不新建任务冒充原任务。尚未在用户真实Harness中证明任意旧会话都能即时热替换入口。

入口就绪后，在原对话告诉L1：**“检查新版，把当前任务升级到兼容版本，保留全部授权、消耗和历史记录。”**

1. L1用`workflow_updates(action=check)`检查发布，用`upgrade_preview`检查当前任务能否迁移。关闭自动更新时check不联网，仍可迁到已经安装/缓存的可用新版。
2. 等当前工具操作完成。预检必须能获得任务、桥和控制器的锁，核对API账本、项目快照、历史证据、源/目标版本及原始授权。
3. `workflow_updates(action=upgrade)`展示准确的版本摘要、任务状态和影响，由真实用户在Harness原生界面批准。取消、跳过、自由文本或模型声称已批准均不生效。既有开工授权绑定旧版本，所以此次确认用于批准具体版本迁移，不改变目标、权限或额度。
4. 控制器再次核对全部快照，通过后记录迁移并选择新版。下一次工具调用提供新规则；L1用workflow_reference读完整AGENTS.md、L1.md及续页。
5. L1重新组织独立需求/计划审核。原先的待澄清、资源评估、追加授权或方案问题仍须按原流程解决。通过后DOT继续未完成工作，生成新候选并重跑所有必需验证。完成的实现任务不会仅因升级重新派工。

实际版本以`workflow_runtime.version`和`manifest_sha256`为准。`task_pinned:true`表示任务固定在原确认或最近一次已批准迁移的版本，并不一定是最初版本。READY只说明新版已就绪。

## 适用范围

| 状态 | 处理 |
| --- | --- |
| 已确认但未初始化；需求/计划审核阶段 | 预检通过后可迁移；原始开工资料保留。 |
| EXECUTING/VERIFYING在工具调用之间暂停，无活动进程 | 可迁移；旧审批/候选失效，保留完成列表和消耗，重新审核与完整验证。 |
| DECISION_PENDING、额度评估或追加授权等待 | 可迁移运行版本，但原阻塞不被解除；先解决相应决定再执行。 |
| 实际执行中、控制器被占用 | 暂不能迁移，等待操作完成；不强杀、不自动重放。 |
| interrupted.json、active_run或未完成API账本 | 拒绝；先走单独的事实核实流程，升级不清除UNKNOWN。 |
| 最终失败/成功/UNKNOWN报告、BLOCKED、DELIVERY_READY | 拒绝；升级不撤销终态或重新授权执行。 |
| 原版本缓存缺失/损坏、项目被未记录修改、证据变化 | 拒绝并保留记录，先核对或恢复准确内容。 |
| 3.3.x及更早任务、手动MCP任务、未列明源版本 | 本版无通用迁移支持，不猜测兼容性或改写旧摘要。 |

3.5.0明确支持原生3.4.0、3.4.1任务迁入，要求准确源版本缓存可用，源数据schema为1。兼容名单在policy/task-upgrades.json；未来版本须新增并测试具体来源。仅允许向前迁移，不做原地降级。

## 保留内容与重新验证

confirmation.json、原始需求、委托、bridge.json不改写。目标、AC、权限、资源总上限、截止时间及后续授权保持；已用次数、API账本、评审次数、修订次数、失败历史、原始证据和已完成任务列表不清零。迁移本身不调用GPT或Codex，不产生产品派工；后续评审、验证照常计入原预算和总时间，额度不足进入L1评估。

旧审批和候选绑定保存在历史中，但不再作为当前通过依据。新版审批重新绑定迁移摘要；新候选ID包含新基线，因此不能复用旧PASS。构建/测试、Doxygen、独立测试、独立审核以及适用的华为合规检查仍须实际执行。需求/方案确需改变时走原修订流程，不能用升级代替需求或权限审批。

## 中断、记录与状态机

迁移状态为：`PINNED → PREVIEW → NATIVE_CONFIRMATION → LOCAL_MIGRATION_PENDING → PINNED_NEW_RUNTIME`。取消或过期预览保持原状态；迁移后运行状态一般转REVIEW_PENDING，已有DECISION_PENDING或未完成事实/范围修订则保留DECISION_PENDING。它不是产品成功状态。

追加的runtime-upgrades.json保存源/目标版本及摘要、原始确认摘要、用户会话、迁移时刻、快照摘要和前一条记录摘要。状态和最终报告列出迁移记录；旧证据完整保留。这是同账户本地审计记录，不是防本机管理员篡改的签名服务。

写入前保存runtime-upgrade-pending.json，包含精确前后状态及迁移日志。迁移中断后所有普通任务工具暂停；`workflow_updates(action=upgrade_recover)`只在当前文件精确匹配已记录前/后内容、项目及其他记录未变化时，完成此前已获批准的本地写入。不会调用模型、重新派工、清除产品UNKNOWN或重置计数。任何意外变化、残留不匹配文件或记录损坏须人工核实，不自动覆盖或回滚产品。已完成迁移不支持自动撤销。

原生界面的确切批准不能由模型参数提供，私有Python管道仅供受信本地入口调用；与现有控制器一致，不构成同账户恶意进程隔离。

3.6.0同时支持3.5.0正常任务迁移。若是未提交初始化的UNKNOWN，普通upgrade仍拒绝；使用独立的[初始化恢复](initialization-recovery.md)预检及原生审核，不借升级自动解锁。

3.6.1增加3.6.0正常任务作为迁移来源；仍需准确原生确认、重新独立审核和完整验证。仅聊天汇报格式可以直接遵循用户偏好，无需为排版强制迁移已有任务。

3.7.0增加3.6.1正常任务迁移来源；先安装ABI5入口。新入口保留旧工具合同以读取已固定任务，新增API评估工具仅在任务实际使用3.7.0后有效。原UNKNOWN、未决API和终态继续拒绝迁移；不能为了取得恢复工具而删除旧记录。

3.8.0增加3.7.0正常任务迁移来源；先安装ABI6入口，再预检并经原生确认升级。已验证使用真实发布的3.7.0代码创建模拟任务后迁移，原确认/委托/资源记录不变，已完成实现不重派，重新独立审查及验证。该验证使用模拟工作模型，不是真实Harness桌面验收。已结案或带旧中断标记的任务仍不可通过升级重开。

3.9.0增加3.8.0正常任务迁移来源，保持ABI6。已用真实发布3.8.0运行包创建隔离模拟任务，验证原生确认迁移、原记录不变、已完成实现不重派及重新独立审核验证。此验证的模型和确认由夹具模拟；旧终态及未决产品操作不借升级自动解除。
