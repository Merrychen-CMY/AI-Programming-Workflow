# DOT处理问题

1. 验证或交付发现问题先报DOT（L2职责）：候选、计划、运行、观察事实和证据。不能直接给开发者派修。
2. DOT核对事实和授权，分析根因，再选择实现、任务/方案、计划/用例、设施、需求或交付路径。未知先诊断，混合问题拆关联子单。
3. 已批准范围内的内部问题自行处理，保留根因、派工、版本和尝试记录。测试维护由独立验证计划职责审阅，不通过删测试或降低标准求通过。
4. 需求/AC变化、权限或预算扩大、无法解决的阻断，整理影响、建议和备选方案，通过L1集中请用户决定。未受影响且仍获授权的任务可以继续。
5. 修复后按影响独立重验；代码/构建输入变化必须新候选。证据满足后DOT关单，保留旧失败。纯授权问题核验真实批准及交付目标，不无理由重跑产品测试。

查表：[L4失败矩阵](../../policy/l4-failures.json)、[L5交付矩阵](../../policy/l5-delivery.json)、[升级](../../policy/escalation.json)、[重验](../../policy/reverification.json)。表中的L2就是DOT的调度职责，L1-V是内部验证计划职责；“新授权”不一律等于“用户再次审核”，已有委托覆盖时按相应审批机制处理。
