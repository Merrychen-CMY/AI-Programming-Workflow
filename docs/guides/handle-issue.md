# DOT处理问题

1. 验证或交付发现问题先报DOT（L2职责）：候选、计划、运行、观察事实和证据。不能直接给开发者派修。
2. DOT核对事实和授权，分析根因，再选择实现、任务/方案、计划/用例、设施、需求或交付路径。未知先诊断，混合问题拆关联子单。
3. 已批准执行计划范围内的普通问题自行处理，保留根因、派工、版本和尝试记录。测试维护由独立验证计划职责审阅，不通过删测试或降低标准求通过。
4. 需求/AC变化、权限或预算扩大、无法解决的阻断，整理影响、建议和备选方案，通过L1集中请用户决定。未受影响且仍获授权的任务可以继续；计划实质范围、方案或必需检查变化也须重审计划。
5. 修复后按影响独立重验；代码/构建输入变化必须新候选。证据满足后DOT关单，保留旧失败。纯授权问题核验真实批准及交付目标，不无理由重跑产品测试。

查表：[L4失败矩阵](../../policy/l4-failures.json)、[L5交付矩阵](../../policy/l5-delivery.json)、[升级](../../policy/escalation.json)、[重验](../../policy/reverification.json)。表中的L2就是DOT的调度职责，L1-V是内部验证计划职责；普通等义维护在既有委托内记录；需求和执行计划由L1代理批准，最终报告由L1核查并交用户审核，实质基线变化须重审。

嵌入式C规范发现使用 [33条规则ID](../../policy/embedded-c.json) 关联证据，按根因分诊，不能只按报错名称派修。计划/检查器问题不得通过删必需测试或放宽容差解决；旧问题基线不得扩张以掩盖新增违规。

6. 当前额度耗尽先停止派工并进入L1评估：在用户上限内调整资源或申请追加授权；无可行方案、授权未获批准且无法继续时，由L1先明确评估并记录终止依据，再生成最终失败/未完成报告提交用户。确认失败报告保持BLOCKED；本任务不自动恢复，后续新任务须明确关联旧报告和消耗。
