# 首次跑通：从一个小需求开始

1. 用户把想法和现有资料告诉L1。
2. L1生成 [统一需求文档](../../templates/requirements.md)，包含可验证AC、范围、预算和交付动作；用户审核批准这一版本。
3. DOT接手批准文档，确认产品位置和真实工具能力，拆一个小任务；内部验证职责形成检查计划。
4. 开发者实现、自测并提交冻结候选；独立验证者或受保护CI执行必需检查。
5. 若发现实现缺陷，验证者报告DOT；DOT分析派修，新候选再独立验证。普通修复不让用户重新审需求。
6. 若发现AC不清或需要超出范围，DOT整理事实与建议，通过L1请用户决定，修改需求则更新版本和批准。
7. 通过后DOT提供验收结果、产物、使用说明和剩余风险；核对已有授权后执行覆盖的交付动作，否则准备具体申请。

第一次优先确认这条主线和一次真实失败回流。软件任务不要求硬件；若批准AC包含HIL，缺少设备的必需检查必须标为阻断，不能伪装通过。

随后按 [进阶说明](../advanced-profile.md) 接入实际需要的自动化。原 [48项拒绝测试](../../policy/rejection-tests.json) 用于相应系统能力验收，仓库静态检查不代表它们已执行。

嵌入式C试点先确认 [规范V1.3](../../standards/embedded-c/README.md) 的适用范围和风险，优先接入现有quick/full检查；只有对应需求或风险需要时再启用hil/soak。代码风格、可读性和资源/时序审查不能因为工具尚未自动化而标为通过。
