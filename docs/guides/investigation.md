# 问题调查与材料超限处理

问题交给 L2 分析。尚未查明原因表示调查工作还没完成，不是任务结束理由。当前根因分类取消 `unknown`；`needs_analysis` 表示 L2 的调查待办，不是一个已经确认的根因。不得伪造根因，也不得为通过流程删掉原始失败。

## 正常处理

1. L3/L4/L5 提交观察、失败证据和执行状态给 L2。
2. 控制器保存完整回流材料，生成明确标注省略部分的摘要，附原件路径和 SHA-256。不会把全部历史命令输出无限重复塞入 API。
3. L2 能确认原因时，按职责派发；还缺可获取依据时，先直接查询或委派调查，并按需读取原始证据。仍需改变基线、权限或资源时，带已查证事实、尝试结果和具体方案进入 `DECISION_PENDING`，由 L1 主动协调处理，不能只交疑问清单。
4. L1 判断继续解决的收益，在授权内整理证据、补充事实、调整方案和当前额度。需要扩大文件/设备/网络权限、修改目标或改变用户明确截止时间时，调用现有追加授权流程，由用户原生确认。
5. 受影响基线经修订、独立审核及 L1 批准后继续。保留全部历史、累计消耗和截止时间；不能靠换任务或重启重置预算。
6. L1 明确评估没有可行方案、用户要求结束，或全任务资源/截止限制无法获得合法调整时，才提交最终报告。不能仅因暂未查明原因、材料超限、当前额度不足或需要授权而调用 `l1_stop`。

## 材料超限

API 输入上限仍为 250000 字节。标准回流视图目标为 18000 字节；异常结构仍可能超过总上限，此时必须走明确拒绝，不能静默截断已批准需求。

- 超限在请求登记和发送之前检查：`API_INPUT_TOO_LARGE`、`NOT_SENT`、`COMPLETED_REJECTED`。
- 保留 `input-rejections/` 记录，不增加这次 API 调用次数，不产生产品执行，也不新增中断锁或最终报告。
- 规划前超限进入 `PLAN_REJECTED`；初始化后根因分析超限进入 `DECISION_PENDING`。原失败和累计实现次数保留，不重新派工来取得同一份日志。
- L1 用 `dot_read_record` 分页读取 `run/triage-inputs/` 中的原件，根据问题选择必要证据，不能将摘录说成全文审查。确需新增事实或修改基线时沿用 `l1_add_facts`、`dot_plan`、`l1_revise` 和独立审核。
- 这类未发送的本地拒绝不需要 `l1_review_api` 重试授权。该工具继续处理已经登记的网络/API 异常。

## 操作状态与根因分类分开

操作是否执行完成必须如实记录。产品进程结果尚未确认时，L2 可以只读分析已有证据，控制器保留原 `active_run`，分析活动不能覆盖它。此类问题同样先进入调查决策，不能以尚未查明原因自动结案；但 L1 的评估或范围授权不能替代核实旧进程与副作用，不能自动重新运行产品操作。

本地运行器的人工 `reconcile` 保留兼容。3.11.0原生Harness新增 `l1_prepare_recovery` → `workflow_recover_operation`：L1提交真实核实证据，系统检查旧进程，用户审核准确方案后归档原记录并恢复到调查/独立重审。它不重放产品操作，不将旧UNKNOWN改成成功，也不能撤销最终报告。旧材料中的历史分类保持原样，新记录采用新的调查规则。

原始记录是本机审计材料，不是签名服务。摘要、哈希和分页不证明模型理解正确；真实环境与产品验收仍需实际执行。

非成功结案规则（3.10.0）：L2 可以暂停操作、提交问题和建议终止，不能直接把整个任务判为最终失败。遇到问题先根据证据在现有权限内思考解决方案，记录已考虑方案、预计收益、核验步骤、资源及权限缺口；可执行的修复仍按原分工派 L3/L4。证据不足应提出有边界的调查方案，不能以“未知”替代分析并结束。超出 L2 权限时，将方案交 L1 评估；L1 在授权内协调，越界主动向用户申请。所有非成功结案（FAILED、INCOMPLETE、UNKNOWN）都必须先经过 L1 明确评估。控制器自动错误及旧预算耗尽只暂停，不生成最终报告。l1_stop 的 reason 使用 templates/l1-closure.example.json 所示 JSON 字符串，记录方案、证据、权限、资源和终止依据；普通理由文本会被拒绝且不结案。成功验收门禁、原始失败、累计消耗和未决操作保护保持有效。详见 docs/guides/l1-closure.md。

3.11.0的可执行恢复入口与报告门禁见[完整流程与恢复](flow-recovery.md)：新原生任务强制动态额度和需求先审后规划；问题待决使用只读调查和L1恢复决定，真实中断须核实后原生批准；不重开最终报告。

## 3.19.1 可执行的材料恢复

完整证据与请求材料分开。控制器对规划调查材料采用 32000 字节视图，对历史额度/授权变更和初始化恢复分别采用 8000 字节视图，对计划拒绝反馈采用 16000 字节视图。超出时原件写入 `api/materials/`，返回路径、SHA-256 和明确省略标记。当前需求、当前权限、额度和审批摘要不作为普通日志截短。

DOT 内部 `read_evidence(path, sha256, offset)` 读取受控记录，每页返回 next_offset；路径范围及摘要不符会拒绝。它不是新的 Harness 工具，也不提供批准能力。普通工具结果视图目标 16000 字节，发送前根据完整请求总量与40000字节历史视图目标，先收缩较早的已完成工具输出，必要时仅保留原件引用。保留每个 call_id、全部响应和推理协议项目，不重复执行工具；原始证据按需读取，不能把省略内容当成不存在。页数、推理项目或基线本身仍可能过大，总输入检查继续有效。

L1 收到残余 `API_INPUT_TOO_LARGE` 后必须执行返回的 recovery.steps：先看分项大小，定位需求正文、补充材料、工具历史或工具定义中的主要占用，精简重复叙述并保留证据引用。L1 可以自己读文件和整理交接，也可以组织 L2 调查，不能因 DOT 暂时收不到大请求而把处理责任交给用户。

给 L1 的状态回复也只带调查摘要与原件路径；超过 32 条时标注省略数量，不重复发送命令日志。每条调查同时区分原记录内容摘要与文件 source_sha256，DOT 读取文件时使用后者。重审需求期间状态优先显示当前审核阶段；通过后明确提示 dot_plan，旧规划拒绝保留但不冒充新的需求否决。

已批准需求不是普通日志。确需压缩它时，L1 逐项比较原始目标、参数、硬约束、AC、权限和未决事项，形成等价的新稿；开工前用 `l1_prepare_requirements` 和 `l1_approve(requirements)` 重审，初始化后按已有修订流程重审受影响基线。无实质越权不需要重新让用户确认开工；不能以“精简”为由删除验收项或把未知事实写成已确认。

没有自动删除历史、扩大资源、重放未知操作或撤销最终报告。L1 对真实剩余障碍必须继续分析并提出方案；材料超限本身不能证明无可行方案。最终 Markdown 只显示结论、未完成项、主要问题、用量及调整摘要，完整 JSON 保留并提供索引。

材料按阶段去重、文件页复用、重复失败及恢复建议见[提效与故障处理](workflow-efficiency.md)。当前事实不能静默覆盖授权或AC。

3.21.0对旧版JSON字符串/摘要引用提供只读解包视图，逐跳核对原件哈希；原文件不改写。分页offset属于返回的视图，超过末尾返回FAIL，不能把空页当新证据。每次请求账本记录压缩前后文本字节数及主要分项；字节不是token，也不是账单金额。

3.23.4证据交接修复：历史压缩保留最新工具结果的工作视图，read_evidence最新页正文、摘要和分页游标原样送达模型；旧结果仍可归档。宽调查结果优先保留结论、原因及后续动作。软预算不能把刚请求的正文再次压成引用；硬上限仍在发送及计费登记前返回NOT_SENT，不删除基线、不变更授权。
