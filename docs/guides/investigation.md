# 问题调查与材料超限处理

问题交给 L2 分析。尚未查明原因表示调查工作还没完成，不是任务结束理由。当前根因分类取消 `unknown`；`needs_analysis` 表示 L2 的调查待办，不是一个已经确认的根因。不得伪造根因，也不得为通过流程删掉原始失败。

## 正常处理

1. L3/L4/L5 提交观察、失败证据和执行状态给 L2。
2. 控制器保存完整回流材料，生成明确标注省略部分的摘要，附原件路径和 SHA-256。不会把全部历史命令输出无限重复塞入 API。
3. L2 能确认原因时，按职责派发；还缺依据时，说明缺少哪些事实、需要哪些权限或资源、下一步调查建议，保持 `DECISION_PENDING`，由 L1 协调。
4. L1 判断继续解决的收益，在授权内整理证据、补充事实、调整方案和当前额度。需要扩大文件/设备/网络权限、修改目标或提高全任务上限时，调用现有追加授权流程，由用户原生确认。
5. 受影响基线经修订、独立审核及 L1 批准后继续。保留全部历史、累计消耗和截止时间；不能靠换任务或重启重置预算。
6. L1 明确评估没有可行方案、用户要求结束，或全任务资源/截止限制无法获得合法调整时，才提交最终报告。不能仅因暂未查明原因、材料超限、当前额度不足或需要授权而调用 `l1_stop`。

## 材料超限

API 输入上限仍为 250000 字节。标准回流视图目标为 60000 字节；异常结构仍可能超过总上限，此时必须走明确拒绝，不能静默截断已批准需求。

- 超限在请求登记和发送之前检查：`API_INPUT_TOO_LARGE`、`NOT_SENT`、`COMPLETED_REJECTED`。
- 保留 `input-rejections/` 记录，不增加这次 API 调用次数，不产生产品执行，也不新增中断锁或最终报告。
- 规划前超限进入 `PLAN_REJECTED`；初始化后根因分析超限进入 `DECISION_PENDING`。原失败和累计实现次数保留，不重新派工来取得同一份日志。
- L1 用 `dot_read_record` 分页读取 `run/triage-inputs/` 中的原件，根据问题选择必要证据，不能将摘录说成全文审查。确需新增事实或修改基线时沿用 `l1_add_facts`、`dot_plan`、`l1_revise` 和独立审核。
- 这类未发送的本地拒绝不需要 `l1_review_api` 重试授权。该工具继续处理已经登记的网络/API 异常。

## 操作状态与根因分类分开

操作是否执行完成必须如实记录。产品进程结果尚未确认时，L2 可以只读分析已有证据，控制器保留原 `active_run`，分析活动不能覆盖它。此类问题同样先进入调查决策，不能以尚未查明原因自动结案；但 L1 的评估或范围授权不能替代核实旧进程与副作用，不能自动重新运行产品操作。

现有本地运行器的人工 `reconcile` 允许在调查暂停状态，经真实操作者核实后记录恢复依据；原生 Harness 没有新增通用产品中断解锁工具。本版不自动迁移、删除旧 UNKNOWN 或撤销已生成的最终报告。旧材料中的历史分类保持原样，新记录采用新的调查规则。

原始记录是本机审计材料，不是签名服务。摘要、哈希和分页不证明模型理解正确；真实环境与产品验收仍需实际执行。

非成功结案规则（3.10.0）：L2 可以暂停操作、提交问题和建议终止，不能直接把整个任务判为最终失败。遇到问题先根据证据在现有权限内思考解决方案，记录已考虑方案、预计收益、核验步骤、资源及权限缺口；可执行的修复仍按原分工派 L3/L4。证据不足应提出有边界的调查方案，不能以“未知”替代分析并结束。超出 L2 权限时，将方案交 L1 评估；L1 在授权内协调，越界主动向用户申请。所有非成功结案（FAILED、INCOMPLETE、UNKNOWN）都必须先经过 L1 明确评估。控制器自动错误及旧预算耗尽只暂停，不生成最终报告。l1_stop 的 reason 使用 templates/l1-closure.example.json 所示 JSON 字符串，记录方案、证据、权限、资源和终止依据；普通理由文本会被拒绝且不结案。成功验收门禁、原始失败、累计消耗和未决操作保护保持有效。详见 docs/guides/l1-closure.md。
