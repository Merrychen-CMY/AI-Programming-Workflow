# 执行范围、进度问询和Markdown报告

本规则约束L1、DOT/L2及其独立执行会话，不新增审批环节、权限、预算或验收项。华为规范、Doxygen、独立验证及真实证据要求继续有效。

## 每次派工的六条规则

1. **最小改动**：Make the smallest change that fully solves the task. Do not add abstractions, fallbacks, defensive guards, refactors, or features unless they are strictly required.
2. **先定范围**：从请求及获批基线列出预期结果、允许修改对象、必须保持的约束和验收条件。路径不清晰时先做最小范围查找，不以读码为由扩展到整个工程。
3. **只读请求就只读**：解释、诊断、评审只排查和报告，不修改代码、不运行测试。独立验证任务有明确计划授权时可执行该计划中的测试；评审者不能因为看到测试命令就顺便执行。角色标签本身不扩大请求权限。
4. **不扩展机制**：沿用现有代码做够用的最小改动，不加兼容层、开关、依赖或抽象，除非完成本任务严格必需且仍在原授权范围内。
5. **做完就停**：完成本次分工后返回DOT，不继续寻找并修复无关问题。发现不等于授权；不影响验收的事项在摘要或审核证据中标为非阻断建议，由L1转用户决定。不得把建议放入强制`findings`触发修复；真正违反AC、硬约束或必需证据要求的问题仍须进入失败处理，不能借此省略已批准的独立验证。
6. **及时问进度并收敛**：独立执行会话连续120秒没有可见进展、且无正在运行的命令时，L2运行器通过Codex App Server在同一会话询问“你正在做什么？”，要求说明当前动作、阻碍和最小下一步，并回到已授权范围。

派工说明使用已有任务说明及验证说明字段，不增加一套用户表单。实现只允许批准路径；验证和审核仍使用独立会话。当前L5由DOT承担验收汇总，没有独立L5 Codex会话；监督机制适用于实际存在的L3/L4及独立审核会话，不能声称询问了不存在的执行者。

## 进度问询的边界

“无可见进展”是运行器观察到的事件状态，不是对模型内部思考的判断。正在运行的构建、测试等命令不被误报为长期thinking；后续命令输出、完成事件或公开进度按实际记录处理。问询只要求可以向用户汇报的动作与阻碍，不要求内部思维链。

协议确认接收问询只代表送达，不代表执行者已经回复、完成或通过验证。问询仍发生在原会话，不另派写入者，不重放任务，不追加实现次数、不重置既有超时或总额度。原有超时、进程核实、UNKNOWN及L1评估规则保持有效；监督不能成为自动结案或扩大权限的理由。

## L1的报告交付

每次实际需求审核、计划审核，以及最终报告提交，都生成独立`.md`文件，包括审核未通过的情况。文件保留本次基线、真实审核结论、问题与证据、已用资源及后续处理，最终报告保留原DOT结果、失败历史、限制和L1结论。尚未开始审核的前置校验拒绝不能冒充一次已完成审核。

工具通过`report_files`返回文件，原生插件向当前聊天提交`deliverables/presented`文件交付事件，宿主在本轮结束后显示文件卡。L1同时在正文给可打开的Markdown链接、结论及需要用户决定的事项；需要最终审核前先输出链接，不以卡片尚未展示为由让用户盲审，也不新增发送批准。仅保存到磁盘或贴摘要不等于聊天文件卡已经显示；交付事件失败时明确文件已保存但尚未提交展示，按真实回执处理。不得为了发送报告改写证据、清除失败或冒充用户批准。

报告可读文件不替代控制器JSON记录及其摘要校验。中间审核仍由L1完成，不因为发送文件增加用户审核关卡；最终仍须先`l1_submit_report`再由`workflow_review_report`取得真实用户审核。文件交付也不授予发布、部署或设备操作权限。

派生Markdown写入失败返回`COMPLETED_REPORT_PENDING`，保留已完成的审核、批准及消耗。修复文件写入条件后，重试原`l1_approve`或`l1_submit_report`只补生成缺失文件，不重派审核、不改原结论。新版最终报告缺少Markdown时不能进行人工确认；旧报告按原规则保留。真正未决操作仍须走原恢复流程，补文件不清除UNKNOWN。

## 各层主动处理阻塞

所有层级都先“查证 → 权限内最小处理 → 核验 → 未解决则带方案升级”。这是一项工作职责，不是新增工具权限，也不要求每个故障都必须尝试写入才能上报。只读审核可以自行找资料、读证据、核实版本；修复产品、运行测试和改变基线仍按原分工与批准执行。

| 层级 | 应主动完成 | 需要交接的情况 |
| --- | --- | --- |
| L1（含L1-V） | 整理精简材料、补充事实、组织调查；完善需求及验证基线，安排独立审核后批准；评估并批准资源调整 | 超出委托的目标、AC、操作权限或明确截止时间变更，向用户提交具体方案 |
| L2 / DOT | 自行或委派查资料、查环境、定位根因；纠正可修正的计划草案；协调依赖，按获批计划派L3/L4处理 | 剩余基线、资源或权限决策，连同已完成调查及方案交L1 |
| L3 | 查明本次实现所需上下文，在授权路径内解决分工涉及的实现问题，执行已授权自测并保留结果 | 跨任务、需求、方案或权限问题交L2；不自行取得验收通过 |
| L4测试 | 查证环境、输入和证据采集问题；执行本次派工已明确包含的设施准备或恢复动作并保留前后证据 | 新设施动作交L2选择已有批准动作或提交L1；产品修复、用例/预期变更统一回L2 |
| L4及其他独立审核 | 自行定位并阅读缺失上下文、原始记录或分页证据，给出有依据的结论及建议 | 新测试或产品修改交L2安排；不得自行运行或改写被审核对象 |
| L5（由DOT承担） | 查找已有证据、补齐报告引用、核对验收汇总与交付目标/授权，解决汇总材料不一致 | 需要新执行、修复或重新授权时回L2协调；不造证据、不自行批准交付 |

一次未解决的阻塞交接使用现有summary/evidence/findings及[交接模板](../../templates/handoff.md)，包含：具体阻塞；已尝试动作或为什么无权执行；实际结果和证据；最小解决方案及核验方法；所需决策及下一责任层。DOT分诊继续使用现有solutions等结构化字段。不要只写“缺资料”“环境异常”或“请L1处理”。保留原始失败，不能通过摘要隐藏未通过项。

重试前必须有新证据或条件变化，并确认操作结果、剩余额度及既有恢复入口允许；不得原样循环重试。额度耗尽交L1评估而非自行延长；未决操作先核实，不盲重放。不影响阻塞、且控制器允许的独立工作可以继续；不能绕过全局暂停启动派工。

实际接线：原生L1加载harness/prompt.md、AGENTS.md和L1.md；GPT/DOT API及Codex执行/测试/审核/调查会话使用scope_constraints中的共同规则与角色规则。已有草案纠正、材料有界视图、L2分诊派修、设施恢复、L1额度评估及报告补生成入口继续使用。此次没有新增通用自动重试器或状态绕过入口；模型是否能解决具体环境故障仍需真实任务证据验证。

各层主动排障的实际材料处理、复用边界及故障步骤见[提效与故障处理](workflow-efficiency.md)。
