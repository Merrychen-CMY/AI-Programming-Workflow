# 核心规则

本页为短版规范。结构化约束见 [workflow.json](../policy/workflow.json)，完整技术条件按 [导航](../START_HERE.md) 读取。MUST 表示必须，MUST NOT 表示禁止；示例和建议不构成授权。

## R01 双 L1

Product L1决定产品需求和验收目标；L1-V维护验证需求、计划及用例基线。开工前准备预设计划，门2冻结候选后生成绑定该候选的L1-V实例。候选重绑可使用明确的预授权；没有预授权就按既定审批机制取得批准。计划语义变化不得套用仅允许候选重绑的授权。

## R02 唯一回流入口

L4/L5发现的问题 MUST 先登记给L2。L2负责接收、分析根因、分类、拆任务、协调方案与依赖并调度。L4/L5 MUST NOT 绕过L2向L3派发正式修复。立即停止危险操作可按已有紧急停止规则执行，但恢复仍须经过L2和适用授权。

## R03 按根因决定处理层

需求/AC → L1；任务拆分/方案/依赖 → L2；实现 → L3；测试计划/用例/预期/验证器逻辑 → L1-V；测试设施/证据采集 → L4；交付目标/授权 → L5准备申请，由授权人决定。安全事项升级授权安全负责人。未知根因BLOCKED，混合根因拆子单，上游基线先定。

## R04 门禁独立

G1批准开工范围；G2确认冻结候选；V0核对有效验证授权；G3核验完整可信证据；G4批准确切候选、证据、动作和目标。L5汇总和申请，不能自批。流程角色不等于真实审批身份。不能用自然语言、手写字段或静态检查代替认证回执。

## R05 不可变候选与基线

实现、依赖、工具链、构建配置、产物或集成起点变化 MUST 产生新candidate_id。新候选不得复用旧候选PASS；重新通过G2、L1-V绑定、V0和必需验证。产品不变、仅计划或验证器语义改变可保留候选，但要新计划授权并重跑全部必需验证。

## R06 独立验证和证据

L3自测不能代替L4验收。检查绑定产品/计划/候选和运行身份。零测试、必需跳过、证据缺失、版本不匹配、身份未知都不放行。保留全部尝试与失败；文件哈希证明完整性，不能单独证明真实执行。

## R07 重验与关单

L3完成后问题状态为待独立验证。G3依据处置决定和重验证据判断失败是否已处置，随后L2关单；不能以先CLOSED作为G3前置条件。纯交付授权/目标问题经审批服务与守卫核验、L5复核后关单；若影响验证假设，再交L1-V/L4。

## R08 重试与恢复

初始建议：实现总尝试上限3次（含初次），同根因失败达到2次暂停并升级，设施最多额外重试2次。预算维度独立，重启不清零。UNKNOWN必须先查询旧运行、写入者、设备会话或真实交付副作用，不能盲目重发。

## R09 变更与授权

需求/AC变化提交L1；测试计划/用例变化提交L1-V；权限/预算扩大提交对应授权人。merge、release、生产刷写不互相推定授权。目标漂移由L5报L2，按是否改变集成内容决定新候选/重验或重新审批。

## R10 规范仓库和实际运行分离

本仓库只交付规则、模板和静态检查。真实项目仍需实现/接入控制器、审批服务、可信证据存储、wrapper及交付守卫。规范仓库CI通过不等于产品验收通过。拒绝测试清单的NOT_RUN不能改成PASS而不附真实结果。
