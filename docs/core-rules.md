# 核心规则

入口见 [L1](../L1.md)、[DOT](../DOT.md)，状态与授权见 [simple-flow.json](../policy/simple-flow.json)，内部回流见 [workflow.json](../policy/workflow.json)。

1. 用户描述需求，L1给出需求与验收目标供审核；批准绑定确切版本和摘要。
2. DOT形成执行计划供用户审核；需求批准不允许直接实现。计划明确任务/依赖、开发/测试/审核分工、必需检查、预算及交付边界。
3. 开发、独立测试、独立审核使用不同执行会话；自测不是独立验证，角色标签不是身份隔离。
4. 失败全部先到DOT，核对证据与根因再调度。需求/AC回L1；方案/依赖由DOT；实现派开发；计划/用例交L1-V；设施/证据交验证职责。
5. 范围内普通修复不重复请用户批准；需求/AC变化先重审需求，已审计划实质变化重审计划。内部维护不得放宽要求。
6. 代码、依赖、构建输入或产物变化生成新候选；独立测试和审核证据绑定实际候选，不能复用旧PASS、删除失败或将未执行视为通过。
7. 重试和时间/费用有限，重启不清零。达到上限停止自动修复，汇总报告。UNKNOWN先确认旧运行和副作用。
8. 成功、失败及未完成均提交最终报告给用户审核；审核前不得直接DELIVERED。批准成功报告为可交付，批准失败报告保持BLOCKED且不授权继续。
9. 交付动作另核候选、证据、准确目标、授权及真实回执。预授权不能跳过报告审核；merge不推定release或生产刷写权限。
10. 本地终端审核须用户本人输入摘要确认，Agent不得代输；本地状态文件不等于受信审批服务或安全隔离。检查器、模板、Agent总结不授予权限。
11. 嵌入式C采用 [V1.3规范](../standards/embedded-c/README.md) 及逐条清单、Doxygen，按适用性核验。规范CI不证明产品合规；必需证据不足就报告未完成。
