# 11 配置 CI 与受保护分支

将 CI 分为两个权限区：

1. 构建与测试区：运行候选代码，采用临时环境，只能上传本次运行的输出，不能持有审批、签名或合并凭证。

2. 收集与裁决区：运行固定控制仓库版本，校验运行身份和文件后生成回执，调用 govrail；不执行候选代码。

HIL 必需的服务凭证仅注入固定 wrapper 进程，限制额度与作用范围；不能给候选固件或可任意修改的测试脚本读取。签名密钥不能暴露在执行候选代码的同一进程或容器中。

在 GitHub 仓库设置中，为 main 和发布分支设置保护规则：

- 要求通过 PR 合并，禁止直接推送、强推与删除。

- 要求来自受信检查发布者的唯一状态检查 evidence-admission。

- 启用适用的旧审批失效和代码所有者审查，限制绕过权限。

- 保护工作流、控制仓库、验收用例和策略；规则变更单独审查。

- 实现代理无管理员、规则编辑、审批冒认或生产发布权限。

GitHub 支持必需状态检查与分支保护，但管理员默认可能有绕过空间，需要明确配置。[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

pre-push 仅作为提前反馈。它可被跳过，因此服务端门禁必须独立生效；工作分支允许先推送，再生成 CI 证据。[Git push 文档](https://git-scm.com/docs/git-push)

CI 任务依赖按以下顺序配置，而不是把所有步骤塞进一个拥有全部凭证的 job：

```text
校验门1批准和固定控制版本
  → L2 协调实现与集成 → L3 提交代码
  → 受控构建并冻结候选 → 门2
  → L1-V 绑定候选并取得有效授权 → V0
  → L4 软件验证与 HIL → 无论成功失败均保存原始日志
  → 收集器验证来源并封存证据 → govrail 判定门3
  → PASS 时交 L5 汇总风险和申请 → 门4
  → delivery_guard 再校验 → 执行指定动作并记录回执
任一 L4/L5 问题或门禁失败 → L2 接收、根因分析、分类与调度
  → 责任层处理 → L2 校验影响和依赖 → 必要的候选/基线更新
  → 按影响范围由 L4 重验并更新门3，或核验交付授权 → L5 汇总
```

测试失败仍需上传原始日志并执行最终裁决，不能让后续裁决因前序失败而被跳过。取消或失联由监视器保存不完整运行并保持不放行，提交 L2 确认运行状态和恢复路径。L4 只能按 L2 已登记且获授权的恢复策略执行设施重试，不能自行转派 L3。

正式检查需要与确切的合并内容绑定。首次部署建议采用可控的简单策略：冻结主分支起点 B，在 B 上完成集成候选 C；验证并批准 C；交付程序仅在主分支仍为 B 时将其更新为 C。若托管平台不支持这个落地方式，则使用 merge queue 或预先生成的合并候选，并明确记录与实际落地 tree 的一致性。

PR head 通过不能证明最终合并内容通过。目标分支前进、冲突解决、squash 或 rebase 改变被验证对象时，交付守卫停止，L5 向 L2 报告。L2 协调生成新集成候选并重新验证；L5 在新证据齐备后重新申请门4。禁止覆盖 candidate_commit 迁就旧证据。

环境审批可用于发布动作，但是否可用取决于仓库和订阅；单人账号还需注意“禁止自审”可能阻止自己触发的运行。无法使用时，以独立认证或签名审批服务承接，不降低门4条件。[GitHub 环境配置](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
