# 20 统一回流调度与重新验证

本章定义所有 L4/L5 问题的统一入口、根因处理层、升级条件与关闭证据。门禁适配器发现的问题也进入同一 L2 队列。任何矩阵中的“处理层”均指 L2 分诊之后的责任层，不是发现层可直接跳转的目的地。

## 20.1 问题接收与根因分析

L4/L5 先保存原始结果、候选与基线绑定、预期和实际行为、复现条件及影响，提交 issue_id 并阻断相关放行。L2 确认报告完整性，核对 Product L1 与 L1-V 是否一致，再区分实现、方案、计划、设施、证据和授权根因；日志中的 FAIL 或 timeout 不能自动决定处理层。缺证据时由 L2 调度 L4 补充诊断，保持 BLOCKED，不先猜测为实现缺陷。

L2 输出根因结论、可信依据、受影响 AC/模块/候选、依赖阻断范围、处理任务、允许路径、预算、重验范围和升级条件。接收可立即完成，最终定责需有证据；混合根因建立关联子单，由上游需求或计划决定先行，不能在基线未定时并行做相互冲突的修复。

L2 的诊断可以调用 L3 做只读代码分析、L4 做复现、L1/L1-V 澄清语义；诊断任务本身也登记范围与权限。收到 L4 直接要求改代码的消息时，L3 只回传诊断意见并引用 issue_id，等待 L2 的正式任务。

## 20.2 L4 失败场景回流矩阵

本表每行的接收入口都是 L4 → L2。L2 先核实根因，再派往第三列；最后一列为关闭或重新进入验证的最低要求。

| L4 观察场景 | L2 根因判断与阻断 | 分诊后的处理层 | 重验与关闭条件 |
| --- | --- | --- | --- |
| 编译/构建失败 | 区分代码、依赖方案、工具设施；未冻结则阻断门2 | 代码→L3；方案/依赖→L2；验证设施→L4 | 代码/构建输入变更生成新候选；受控构建与必需检查通过 |
| 功能断言失败 | 既定 AC 明确且测试预期正确；记录 FAIL | L3 修复实现 | 新候选；重跑原失败、受影响回归及本轮全部必需项 |
| 性能、稳定性或质量阈值未达标 | 核对阈值来源及测量可信度，不擅改阈值 | 实现→L3；设计协调→L2；产品阈值争议→L1 | 相应基线/候选更新，按新授权完整验证；保留旧失败 |
| 接口不匹配、集成冲突、任务遗漏 | 确认拆分、契约或依赖顺序问题 | L2 重新拆解/协调，再派 L3 | 关联任务全部完成，生成项目集成候选并整体回归 |
| 需求歧义、AC 矛盾或缺失 | 歧义保持 BLOCKED；批准变更后受影响对象 STALE | L1 产品决策 | 新产品基线；L1-V 同步；校验门1后实现/验证 |
| 测试预期错误、用例误报 | 区分产品语义与测试实现错误；不能转成 PASS | L1-V；独立维护者修用例 | 新控制/计划基线和授权；重验全部必需项 |
| 覆盖不足、零测试、必需跳过 | 定位计划遗漏还是设施未执行 | 计划→L1-V；执行设施→L4 | 补齐 AC 映射或恢复执行；全部必需检查产生有效证据 |
| 验证器判定逻辑错误 | BLOCKED；判定逻辑属于验证基线 | L1-V 和独立控制代码维护者 | 固定修正版并重新审批；重算门禁并重跑必需验证 |
| 板卡/治具/网络/云服务不可用 | ERROR；不确定仍在运行则 UNKNOWN | L4 恢复设施 | 确认旧会话/写入者停止；新 run_id；最多 2 次设施重试 |
| 板卡型号、外设或环境不符 | BLOCKED；区分配置错与验证能力不足 | 配置→L4；计划能力→L1-V | 记录设备身份与环境；必要时换治具并更新计划授权 |
| 超时、失联或取消 | 先区分软件超时和设施错误；状态未知不定责 | L4 核对运行；实现确认后派 L3 | 查询原 run/session；无残留后恢复；不并发新写入 |
| 日志缺失或收集失败 | BLOCKED；有可信原始文件才可重新采集 | L4 证据采集设施 | 可验证原件则追加采集回执；不可恢复则重跑检查 |
| 哈希/签名/身份不可信 | BLOCKED 并隔离可疑证据；禁止补写 PASS | L4 及授权安全负责人；逻辑问题交 L1-V | 重建可信来源；无法证明真实运行的证据必须重新产生 |
| 偶发失败、同候选先红后绿 | 保留 FAIL；判断产品不稳定、测试误报或设施故障 | 分别派 L3、L1-V 或 L4 | 按根因处置及批准统计规则重验；禁止只取最后成功 |
| 越权、注入或恶意依赖 | 立即停止危险操作，L2 阻断调度并上报 | 授权安全负责人；产品修复派 L3 | 事件审查、权限恢复批准及独立安全/功能重验 |
| 多个根因或无法归因 | 拆关联子单或保持 BLOCKED；不盲目派修 | L2 协调诊断并按边界升级 | 各根因有证据及处理结果；阻断子单均通过重验 |

## 20.3 L5 验收与交付场景回流矩阵

本表每行的接收入口都是 L5 → L2。L5 对未经批准的动作立即停止；L2 不拥有交付审批权，交回 L5 的事项由 L5 准备材料，再由对应授权人决定。

| L5 观察场景 | L2 根因判断与阻断 | 分诊后的处理层 | 恢复交付的条件 |
| --- | --- | --- | --- |
| 验收汇总发现 AC 未满足 | 按事实缺陷分类，不以报告修饰代替修复 | 实现→L3；产品目标→L1；计划→L1-V | 相应处理、L4 重验、新门3结论及 L5 汇总 |
| 材料缺失或汇总错误 | 区分汇总漏引与原始证据不存在 | 汇总→L5；原始采集→L4 | 修正报告引用；缺原件需重验，不得手工补 PASS |
| 证据陈旧或对象不匹配 | STALE/BLOCKED；停止门4申请或守卫执行 | L4 重验；绑定/计划问题交 L1-V | 当前候选与有效计划的完整新证据、verdict |
| 门3 PASS 但存在未处置失败 | 判定流程或证据集合不完整，阻断交付 | L1-V/验证器维护者；L4补核证据 | 处置失败、独立重验；重新封存与裁决 |
| 交付目标、设备范围或环境变化 | 目标授权失效；评估是否影响验证假设 | L5 重拟申请；涉及验证范围交 L1-V | 新目标、风险评估与门4；受影响检查先重验 |
| 目标分支前进或合并内容变化 | 原候选不覆盖实际落地内容，标记 STALE | L2 协调集成，L3 处理冲突；L5更新申请 | 新候选、完整验证、新门3和门4 |
| 合并已批却申请发布/刷写 | 动作不匹配；不得推定授权 | L5 准备独立动作申请 | 有效新门4；确认产物和目标证据仍适用 |
| 审批缺失、过期、撤销或 nonce 已使用 | 保持待审/拒绝执行；已使用先核对实际结果 | L5 与授权审批人 | 新有效批准或确认既有动作已完成；不重放 |
| 交付风险不可接受或要求扩大范围 | 保留阻断；先明确风险改变了哪条基线 | 产品风险/AC→L1；计划→L1-V；操作目标→L5 | 相应决策、批准与重验；不得由 L5 豁免必需 AC |
| 交付程序失败、部分成功或超时 | UNKNOWN；核实目标与副作用，禁止盲重试 | L5 协调受控交付维护者；L2 管理恢复任务 | 真实状态回执、恢复/回退授权；动作幂等且不重复消费 |
| 用户退回但未说明原因 | 保持 DELIVERY_PENDING/BLOCKED；L2 汇总可选解释 | L5 补齐验收意见；需产品决策则交 L1 | 明确退回原因后分类；不能默认派 L3 或重跑全部测试 |
| 交付后发现缺陷或请求回退 | 保留原交付审计，新建关联 issue 与修复请求 | 实现→L3；需求变化→L1；回退申请→L5 | 新候选按主线验收；回退仅按仍有效授权执行并留回执 |

## 20.4 跨层级升级与争议处理

| 触发条件 | L2 的升级动作 | 恢复前提 |
| --- | --- | --- |
| 产品目标、范围、AC 或产品风险容忍度改变 | 提交 L1，附失败证据、变更选项、成本和影响 | L1 决策形成新版本；重审受影响门1、L1-V 与交付申请 |
| 测试计划、用例、预期、阈值或必需项变化 | 提交 L1-V；与产品 AC 冲突时先升级 L1 | 计划重新批准；新控制版本与候选验证包经 V0 |
| 任务拆分、技术方案或依赖问题 | L2 召集相关技术负责人，记录方案决定并重排依赖 | 仍在授权范围内可继续；触及产品/验证基线则分别升级 |
| 权限、预算或硬件资源超出授权 | 停止新增消耗，提交相应授权人，不自动扩大权限 | 新授权有效并入库；计数不清零，历史成本继续可见 |
| 同因失败累计 2 次或实现尝试总数 3 次 | 暂停自动修复，提交诊断、已尝试方案及剩余风险 | 授权负责人批准继续策略/额外预算，或更改方案/终止 |
| 设施重试已达 2 次或连续未知状态 | 保持 BLOCKED/UNKNOWN，升级设施负责人 | 确认会话、资源和旧写入者状态，获得恢复依据 |
| 分类有争议或存在混合根因 | L2 协调 L1、L1-V、L3、L4 复核，保存异议并拆子单 | 证据支持分类；无法确认则保持 BLOCKED，不强行归为实现缺陷 |
| 安全事件、伪造证据或高风险副作用 | 立即阻断，交授权安全/交付负责人；保留审计 | 风险处置及恢复批准完成，再执行必要独立重验 |

升级不等于所有失败都回 L1：明确且在授权内的代码缺陷由 L2 派 L3；L1 只处理产品决策。L2 也不能把每个失败都重新派给 L3。测试用例的预期是否正确由 L1-V 对照产品 AC 决定，产品语义争议由 L1 决定；设施执行是否可靠由 L4 提供可核验事实。

等待上游决策时仅暂停受影响任务和依赖子图；不相关任务可在原授权内继续。需要新增权限、改变方案基线或进行有副作用的恢复时，不能以“紧急修复”为由绕过审批。L4/L5 可依据已批准的紧急停止规则先止损，再立即登记 L2；这不授权其自行恢复或修改产品。

## 20.5 回流问题单与调度契约

下面是项目自定义最小记录示例。报告者填写事实；L2 通过认证身份写入 triage 与 dispatch；控制器生成事件序号和审计时间。不能让报告方自填 triage_owner 后就获得调度权限。

```json
{

  "issue_id": "ISSUE-001",
  "source_layer": "L4",
  "source_run_id": "RUN-001",
  "candidate_id": "CAND-001",
  "candidate_manifest_sha256": "REPLACE_CANDIDATE_SHA256",
  "product_spec_commit": "REPLACE_SPEC_COMMIT",
  "verification_package_sha256": "REPLACE_VREQ_SHA256",
  "ac_ids": [
    "AC-02"
  ],
  "check_ids": [
    "hil.serial-ping"

  "observed_outcome": "FAIL",
  "expected": "PING returns PONG within approved deadline",
  "actual": "No response",
  "evidence_refs": [
    "REPLACE_IMMUTABLE_RECEIPT_URI"
  ],
  "triage": {
    "owner": "L2",
    "category": "implementation",
    "root_cause": "REPLACE_CONFIRMED_CAUSE",
    "basis_refs": [
      "REPLACE_DIAGNOSIS_EVIDENCE"
    ],
    "affected_tasks": [
      "TASK-001"
    ],
    "resolution_owner": "L3"
  },
  "dispatch": {
    "resolution_task_id": "FIX-001",
    "allowed_paths": [
      "main/",
      "tests/"
    ],
    "launch_sha256": "REPLACE_LAUNCH_SHA256",
    "attempt": 2,
    "reverify_checks": [

```

report_issue 以 source_layer + source_run_id + check_id + failure_fingerprint 去重，只合并重复上报，不能丢弃不同尝试的证据。dispatch_resolution 以 issue_id + resolution_revision + attempt + launch_sha256 幂等；同一事项已有活动修复时返回原任务。分类改变或扩大处理范围须增加 resolution_revision 并重新核验权限，不能覆盖旧决定。

处理任务完成后附代码/控制版本差异、根因与修复对应关系、自测及影响分析。L2 校验所有关联依赖，创建重验任务；L4 提供独立结果，受信验证器生成新 verdict。关闭记录包含关闭理由、处理与重验引用、遗留风险及批准依据。

## 20.6 候选版本与重新验证规则

| 变化类型 | 候选与基线规则 | 必须重新执行 |
| --- | --- | --- |
| 产品代码、依赖、工具链、构建配置、产物或集成起点改变 | 新 candidate_id；旧对象不可覆盖，关联 parent_candidate_id 与 issue_id | 门2；新 L1-V 候选包及 V0；原失败、受影响回归和本阶段全部必需检查；门3和 L5 |
| 产品需求或 AC 变化 | L1 新版本；L2 重做影响分析并更新 launch；L1-V同步；已有候选需重新论证适用 | 受影响门1重新批准；当前基线的 V0、全部必需检查、门3；必要时新候选 |
| 测试计划、用例语义、验证器逻辑或控制策略变化 | 产品内容不变可保留候选；L1-V/控制基线新版本并重新批准 | 新 V0、全部必需验证及门3；禁止用旧计划的 PASS 自动填充新计划 |
| 测试设施恢复，产品/计划/判定逻辑未变 | 可保留候选和计划；新 run_id 与环境记录，L2批准有限恢复 | 受影响检查、环境健康/校准检查；受污染或过期证据全部重验；重封存证据并算门3 |
| 只补充汇总引用，可信原件已完整存在 | 候选与原始事件不变；追加 L5 报告或收集回执 | 核对原始哈希/身份/完整性；证据集合或 verdict 改变则重算门3并更新交付申请 |
| 仅交付动作、目标或审批变化 | L5 更新申请；候选可不变，但先评估验证假设是否仍适用 | 新门4和 delivery_guard；目标环境改变影响验证时先由 L1-V更新计划并由L4重验 |
| 证据到期、身份或来源不可验证 | 候选可不变；旧证据只保留为历史 | 所有过期/不可信检查重新产生证据；无法证明影响边界则全部必需检查重验 |
| 交付后缺陷或回退 | 新问题关联旧交付；修复新候选；回退对象及授权单独绑定 | 修复按完整主线；回退按预批准条件核验并保存实际回执 |

本教程默认采用保守策略：新候选不得沿用旧候选的 PASS；计划或判定逻辑修订后重跑全部必需验证。同一候选、同一批准计划下，仅设施恢复可保留明确未受影响且未过期的受信结果；L2 的影响分析与 L4 环境证据必须证明隔离边界，证明不了就全部重验。快速/完整/发布前套件的差异由事先批准的 L1-V 定义，不能在失败后临时删减必需项。

candidate.control_commit 表示该候选冻结时的控制版本，不得为匹配新测试计划而覆写。L1-V.control_commit 表示本次验收使用的控制版本；计划修订可引用更新版本，V0 分别验证两个版本的来源和兼容关系，而不是要求它们字符串必然相同。产品构建输入若受此变更影响，必须生成新候选。

全部尝试按候选和问题链保留。后续通过不能删除早先 FAIL；只能追加可核验的根因、处置、失效依据和重验证据。若原失败被确认为测试误报，须有 L1-V 新基线及重验依据；若确认为设施故障，须有 L4 的诊断证据和 L2 分类决定。门3只放行没有未处置失败的当前对象。

## 20.7 回流闭环示例

示例一  PING 不返回 PONG。L4 保存 CAND-001 串口日志并报 ISSUE-001；L2 核对 AC-02 和测试预期，确认串口解析代码缺陷，派 L3 修复。L3 提交后由受控构建生成 CAND-002；L1-V 重新绑定、V0通过；L4 重跑原失败与必需回归。门3通过，L2按独立证据关闭问题，L5汇总两次候选历史并申请交付。不存在 L4 直接把任务退给 L3 的步骤。

示例二  预期应为 PONG，但正式用例断言为 PING。L4 报 L2，L2 对照产品 AC 判定为用例错误，提交 L1-V；独立维护者修订用例并重新批准计划。产品不变可沿用候选，L4 按新验证包重跑必需项；保留误报与更正证据，不要求 L3 修改正确产品来迁就错误用例。

示例三  HIL 服务断线与门4后目标漂移。前者由 L4 报 L2，L2调度 L4 查明旧会话已结束后有限重试；后者由 L5 报 L2，若只改变授权目标则交 L5重新申请，若目标分支改变集成内容则 L2协调 L3生成新候选、完整验证后再申请门4。两类问题均不得直接改成 PASS。
