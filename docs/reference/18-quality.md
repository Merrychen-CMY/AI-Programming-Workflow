# 18 强化独立验证与质量门禁

> v2.0使用范围：本章保留原完整技术参考。默认用户流程为L1整理需求、用户批准、DOT执行；本章内部角色和正式工具契约按 [进阶范围](../advanced-profile.md) 适用，不要求用户逐层操作。

## 18.1 独立验收用例治理

正式验收用例来源于 Product L1、AC 和 L1-V 独立验收计划。编程 Agent 可补充开发自测和提出测试建议，但不能决定正式预期、删除必需用例、降低阈值或跳过失败。L4 发现用例或预期缺陷时先报 L2，由 L2 提交 L1-V 修订；独立维护者在受保护 control-repo 实现并审查，L4 再按新基线执行。

- 每个 AC 必须映射到一个或多个 check_id，并说明测试方法、预期结果和证据类型。

- 测试数据、边界值、异常路径和负向用例应有明确来源；关键预期结果由需求负责人或独立测试负责人确认。

- 测试语义、阈值或必需清单变更产生新的 control_commit / acceptance_plan_sha256，经 L2 影响分析、L1-V 批准后重验；若改变产品 AC，先提交 L1。仅运行设施的修复由 L2 调度 L4；一旦涉及判定逻辑，转为 L1-V 事项。

- 另一 AI 的代码审查可以作为辅助信号，但不能替代独立测试、人工确认或外部可观测断言。

## 18.2 代码质量门禁

| 检查项 | 建议门禁 | 适用说明 |
| --- | --- | --- |
| 静态代码分析 | 必需；严重级别缺陷为零或有批准例外 | 按语言和工具链选择固定版本 |
| 编译警告 | 设置项目阈值；新增高危警告阻断 | 嵌入式项目关注未定义行为和类型转换 |
| 内存与并发 | 适用时执行泄漏、越界、栈/堆和竞态检查 | ESP32 关注任务栈、堆碎片、并发访问 |
| 依赖与供应链 | 锁定依赖并扫描已知漏洞/来源风险 | 记录依赖清单和版本 |
| 代码覆盖 | 按模块风险设定语句/分支阈值 | 覆盖率不能单独证明正确性 |
| 关键模块审查 | 安全、启动、电源、通信和升级等模块要求人工审查 | 审查记录绑定候选 Commit |

## 18.3 测试充分性与变异测试

“执行测试数量大于零”只是最低防空检查，不代表测试充分。门3应要求验证器核对测试充分性指标，并在 L1-V 中预先设定阈值。阈值必须按项目风险制定，不应把某个统一覆盖率数字套用到所有项目。

- 需求覆盖：适用 AC 到正式检查的映射完整；每个必需 AC 至少有有效检查。

- 分支覆盖：关键逻辑分支达到项目预设阈值；未覆盖部分必须说明理由并获批准。

- 边界与异常路径：包括边界值、非法输入、超时、断连、资源不足和恢复路径。

- 故障注入：对适用的通信、传感器、存储、电源或网络故障进行注入验证。

- 变异测试：在关键模块适用时，故意注入逻辑变更（例如比较符号、返回值或条件分支变化），确认测试套件能够发现；未被杀死的变异应分析并记录。

- 所有指标都应绑定候选版本、测试套件版本和验证器版本；不得仅提交一张未关联版本的覆盖率截图。

## 18.4 长期稳定性与分级回归

测试分为快速验证、完整回归和发布前验证。每次候选迭代执行当前 L1-V 所列全部必需检查；集成和高风险/量产候选执行相应完整回归或发布前套件。长期稳定性测试可在事先批准的分级计划中规定触发条件，不能在失败后临时删除。新候选不继承旧候选 PASS；不属于本阶段必需项的长时测试必须在计划中说明触发点和交付限制。

- 连续运行/老化测试（例如 24 小时或项目规定时长）。

- 多次复位、掉电恢复和异常重启测试。

- 网络断连、重连、弱信号及服务端不可用测试。

- 高低负载、资源压力和内存趋势监测。

- 异常输入、压力测试和长时间通信测试。

- 必要时覆盖不同硬件版本、治具和批次差异。
