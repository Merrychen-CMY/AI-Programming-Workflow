# 进阶技术参考的适用范围

v2.0默认用户入口是 [L1](../L1.md) 和 [DOT](../DOT.md)。`docs/reference/`的21章保留v1技术基线，供正式控制器、签名审批、govrail、CI、HIL、交付守卫等接入时按需读取，不作为用户首次描述需求前的配置清单。

## 简化模式与进阶模式

| 事项 | 默认简化模式 | 正式自动化接入 |
| --- | --- | --- |
| 用户审核 | 一份带执行范围的需求文档 | 可由审批服务登记同一份批准内容 |
| 验证计划 | 内部职责形成、版本化、按委托维护 | 独立控制仓库、签名验证包和V0 |
| 运行状态 | DOT维护可追溯任务/候选/问题记录 | 持久化控制器、幂等、并发锁与恢复 |
| 验收 | 独立验证者或受保护CI，真实检查和证据 | govrail/证据服务形成受信判定 |
| 交付 | 核对真实有效授权；范围内执行 | 守卫校验审批/预授权策略并绑定确切对象 |

这些是接入成熟度差异，不允许把不具备的能力写成已经具备。产品启用了正式门禁就必须满足，不能切回“简化”绕过。高风险动作没有所需能力或有效授权时保持阻断。

## 内部层级如何理解

- Product L1仍负责产品需求/AC；用户是实际批准人。
- L1-V是内部验证需求/计划基线职责，不增加一个用户沟通入口。
- DOT承担L2接收、根因分析、拆分、协调、依赖及派工；同时承担L5汇总/风险/申请。
- L3负责实现；L4负责独立验证和设施/证据。DOT合并入口不合并二者的执行身份。
- L5申请不能自批，审批服务或授权人保持独立；已有有效预授权可以由守卫按条件核验，不能由DOT自行生成权限。

## 如何读原技术章节

章节中“控制器”“受信回执”“L1-V批准”“门4批准”等描述，指相应正式接入契约；不能推断用户必须手工操作每个内部对象。新版本明确区分：用户对需求/权限做决定，内部在委托范围内版本化计划、绑定候选、验证授权。

仅候选重绑的授权不覆盖计划语义变化。计划语义变化仍须新计划授权并重验；是否需要用户再次确认取决于既有委托是否覆盖，涉及AC变化必须由用户决定。交付审批可以针对确切对象单次批准，也可以采用用户明确批准、由既有执行系统支持的有限策略；策略核验须绑定实际候选与证据，不能用泛化的“全权处理”替代。

冲突处理：明确采用的模式和项目已有保护决定适用范围；同一适用范围内的规则或批准基线矛盾时停下报告，不自行降级。保留16/12回流矩阵和48项拒绝测试清单，不代表所有项目第一天都要部署全部基础设施。
