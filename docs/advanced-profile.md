# 默认流程与正式集成

默认3.0流程采用L1代理批准需求/执行计划及范围内变更，用户只审核L1最终报告。Product L1、内部L1-V和L2～L5职责保留。21章继续提供控制器、签名审批、govrail、CI、HIL和交付守卫的技术参考。

| 边界 | 本仓库默认实现 | 正式环境仍需落实 |
| --- | --- | --- |
| 中间批准 | L1工具调用，独立只读审查，固定委托/摘要 | 被现有审批服务认可的代理身份、权限及委托凭证 |
| 最终报告 | L1提交，用户终端确认摘要 | 受保护的用户审批渠道 |
| 模型与执行 | GPT API规划/调度/根因；独立Codex会话 | 所需账户、工具及受保护工作环境 |
| 证据 | 不可变候选、真实测试/文档输出、独立审核 | 可信采集/签名、CI、设备与仪器证据 |
| 交付 | 没有外部交付执行器 | 精确动作/目标授权、守卫及真实回执 |

原文中的人工Ready/签名服务不是当前默认的中间人工检查点，也不能靠改提示冒充身份；需在正式服务配置真实委托映射，无法映射就报告接入受阻。现成dsh-spec-collab不提供AI Ready批准，见 [接入说明](guides/l1-harness.md)。

G1仍需需求和计划批准，但默认主体为受委托L1；G3仍需独立证据；G4仍需用户最终成功报告审核及具体动作授权。失败确认不授权继续；预算和明确用户约束不可被代理改写。已有保护不会因采用简化流程被关闭。

历史CLI人工审批仅供兼容既有运行；不是3.0的默认使用入口。原技术示例/章节不得被描述为已经部署的真实服务。
