# DOT执行计划：待填写

状态：DRAFT。计划ID、版本、内容摘要：待填写。关联需求ID、版本、摘要及L1代理批准及独立审查来源：待填写。

本计划是可读内容指引；使用本地运行器时将全部实质内容写入 [JSON计划](local-execution-plan.example.json) 的说明及结构字段，L1审核的是该JSON及绑定需求的摘要。本计划由GPT/DOT准备给L1审核并批准；需求批准只允许编排，计划批准才允许产品实现。可读内容与运行配置应来自同一版本，不能批准一份说明却执行另一份配置。

## 1. 目标、方案及边界

产品仓库与起点、技术方案、保留行为、禁止动作、需求未决项：待填写。

每项分工明确预期结果、允许对象、必须保持的约束及AC；路径不清只做最小查找。派工保留原文：**Make the smallest change that fully solves the task. Do not add abstractions, fallbacks, defensive guards, refactors, or features unless they are strictly required.** 按[执行范围约束](../docs/guides/execution-scope.md)沿用现有机制，不加非必需兼容层、开关、依赖或抽象。

`allowed_paths`：填写允许实现修改的仓库相对路径前缀数组；只包含本次已批准范围。实现完成后核对实际文件差异，超范围阻断并交DOT处理，不能默默扩展白名单。差异检查不是操作系统安全隔离，扩大范围须重新审核计划。

三类执行者使用独立会话，记录真实身份。默认单任务串行；独立会话不等于账户权限隔离。写入者唯一，测试/审核不得改产品代码或验收基线。

解释、诊断、评审只排查和报告，不改代码、不运行测试；评审者看到计划中有测试不等于获得执行授权。独立验证任务只执行本计划明确授权的检查。完成本次分工即返回DOT；非验收问题只作非阻断建议交L1转用户决定，不顺手修复，不作为必须修复的findings。真实AC或硬约束失败仍须报告。

执行会话连续120秒无可见进展且没有命令运行时，L2运行器在原会话询问“你正在做什么？”，取得公开的当前动作、阻碍和最小下一步；记录问询和后续进展，不索取思维链，不把送达当回复，不增加超时或额度。L5由DOT汇总，没有独立L5 Codex会话。

JSON的tasks仅列L3实现派工，可显式标记role=implementation；测试、构建、Doxygen生成、HIL和独立审核写入verification及相应检查说明。文档注释修改可以属于实现，生成/检查文档属于验证。所有AC与必需证据必须保留，不能为适配预算改名隐藏任务或合并独立职责。

## 3. 检查、环境和证据

必需测试/审核、独立期望、精度/时序/安全判据、环境及真实工具版本、执行数量/发现数量、适用规范条款、设备条件、证据位置：待填写。缺设备或必需检查能力必须标明阻断，不能用退出0或文字PASS替代。

`verification.test_command`：填写明确本地测试命令的argv数组，L1审核命令及调用的测试入口；控制器用shell=False独立执行，保存真实退出码和输出。禁止在测试入口夹带部署、烧录、网络发布等动作。测试Codex仍执行test_instructions指定的独立检查并保留证据，不能只打印预期摘要。

`verification.test_report_format`：按实际输出选择unittest、pytest或ctest；必须可解析非零实际测试数量。独立审核核对测试入口和AC覆盖，不把解析成功等同于充分性证明。样例占位环境和命令必须替换为真实项目配置后再审核。

执行前确认可信开发机、已审核测试脚本和本地账户权限范围。参数数组及事后差异检查不提供服务器鉴权或对恶意同账户进程的安全隔离。

## 4. 预算与失败处理

分别填写用户授权总上限和L1当前分配：实现派工、同因失败阈值、设施重试、单次超时、L1审核、修订、API请求、单次输出及总经过时长。绝对截止时间由用户确认；硬件/交付权限另核对。L1在上限内调参，重启和修改计划不重置计数。统一货币硬限额尚未实现，不能以次数替代金额保证。

implementation_attempts是整个任务累计L3派工上限：已用次数 + 新计划初始任务数必须不大于上限。3次不是3轮或每任务3次；列3个初始任务时没有修复余量。完整草案校验失败进入PLAN_REJECTED，保留诊断与API消耗，按[恢复指南](../docs/guides/plan-rejections.md)修正；既有控制器修订前不写新基线或改变批准。

问题统一交DOT根因分析再派工。普通修复可在本计划范围内执行；需求/AC变化先重审需求，计划实质范围/方案/检查变化重审计划；仅在授权内调整当前资源不改产品基线。额度耗尽先L1评估，越界须用户明确批准；无可行方案或无法核实才提交最终报告。

## 5. 候选、交付和风险

冻结方式、代码/依赖/构建输入/产物摘要、测试与审核绑定、拟交付动作和准确目标、已授权范围、风险及回退：待填写。最终报告经用户审核才允许进入可交付状态；本地运行器不执行外部交付。

## 6. L1代理批准记录

L1批准的计划版本与摘要、绑定需求摘要、真实批准来源/时间、明确变更事项：待填写。保持DRAFT直到独立审查和L1批准完成；记录原始委托、L1/审查会话及证据，不能冒充用户批准。修改已批准文件使原批准失效；计划说明与可执行配置一并纳入摘要。

本次实际计划审核生成的Markdown文件、内容摘要、当前聊天文件交付事件及可打开链接：待填写。卡片在本轮结束后展示，审核前先给链接；事件失败不得声称卡片已展示，发送报告不增加常规中间用户审批。

Doxygen补充：引用[DOX采用清单](../standards/embedded-c/v1.3/doxygen/README.md) revision 1和仓库commit，冲突以华为为准。DOT准备`verification.doxygen`中的实际工具路径、精确版本、自有源码include范围及超时，纳入原执行计划审核；L4检查工具报告和语义，新增/修改源码后重新验证。

项目约束补充：[PC-U01～U26](../standards/embedded-c/v1.3/project-constraints/README.md)。DOT在现有任务与review_instructions中记录适用项/理由、检查对象、期望及证据；重点验证if拆分后的调用顺序与短路、注释事实、布尔兼容性和清理依赖。清理/流程图/仅文件清单等条件项不默认每次执行。规范摘要变化使旧批准失效；修改获批内容后按现有L1路径重审。

沟通遵循[合作沟通约束](../docs/guides/l1-dot-communication.md)。提交L1时先给方案与待决项，再给相对已共享基线的变化、影响和依据；完整批准内容仍保留，提案不是批准。无需新增用户表单或工具参数。

面向L1的方案需保留反例、权衡和不满足项，不以突出优势为由删减必需验证或改换AC。L1的[用户表达规则](../docs/guides/l1-user-expression.md)仅用于可读说明，不改写本计划、执行参数或验证证据。

## 运行版本

记录workflow_runtime中的实际版本和MANIFEST摘要；已开工任务使用原确认或最近一次原生批准迁移绑定的版本。列出每次迁移的源/目标摘要、授权、失效审批、重新验证及实际新增消耗；历史PASS不能替代新版验证。说明已下载但未应用的更新，不把更新状态写成产品验收结果，不因更新重置授权、消耗或失败证据。

初始化恢复：记录是否发生受控恢复及当前生效基线。基线变化后使用新的计划并重新独立审查；不复制旧批准、旧PASS或清零消耗。

API异常按[评估与恢复规则](../docs/guides/api-recovery.md)处理。记录API等待调整理由、前后值、请求诊断、原生决定、累计次数、已报告用量及未知用量；不能把超时等同于未发送或零费用，不以重试绕过独立审核。

按[正常开工链路](../docs/guides/normal-start.md)引用控制器原始记录；累计消耗注明时间点，不把历史快照差异当作消耗清零。系统已有证据由控制器随审查包传递，不要求用户重新提供。


3.9.0调查规则：问题统一交L2调查；尚未查明原因不得自动结案。取消根因分类unknown，needs_analysis表示L2调查待办，缺资料、权限或资源交L1解决。L1在授权内推进，越界主动申请用户原生授权，有必要继续解决时保留任务；仅评估无可行方案、用户结束或无法调整的全任务限制才提交最终报告。材料超限返回NOT_SENT/COMPLETED_REJECTED，不产生本次API消耗或最终UNKNOWN；完整证据保留并分页读取，摘要明确标注。操作执行状态仍如实记录；只读调查不能清除未决产品操作或重放写入。详见[调查与材料处理](../docs/guides/investigation.md)。

非成功结案规则（3.10.0）：L2 可以暂停操作、提交问题和建议终止，不能直接把整个任务判为最终失败。遇到问题先根据证据在现有权限内思考解决方案，记录已考虑方案、预计收益、核验步骤、资源及权限缺口；可执行的修复仍按原分工派 L3/L4。证据不足应提出有边界的调查方案，不能以“未知”替代分析并结束。超出 L2 权限时，将方案交 L1 评估；L1 在授权内协调，越界主动向用户申请。所有非成功结案（FAILED、INCOMPLETE、UNKNOWN）都必须先经过 L1 明确评估。控制器自动错误及旧预算耗尽只暂停，不生成最终报告。l1_stop 的 reason 使用 templates/l1-closure.example.json 所示 JSON 字符串，记录方案、证据、权限、资源和终止依据；普通理由文本会被拒绝且不结案。成功验收门禁、原始失败、累计消耗和未决操作保护保持有效。详见 docs/guides/l1-closure.md。

3.11.0流程顺序与恢复：新原生任务强制动态额度。开工确认并分配额度后，先l1_prepare_requirements → l1_approve(requirements)，通过后才dot_plan → dot_initialize → l1_approve(plan) → dot_run。初始化承接原需求独立审核及消耗，不重复审核。DECISION_PENDING使用dot_investigate继续只读分析，L1用l1_resume_decision选择有证据的恢复方案；旧操作未核实时先经原生恢复核对，不能重放。修订保留不受影响的已完成实现，候选与验证随基线重新核验。开工前后报告均先l1_submit_report再由用户审核；非成功结案须真实任务证据。新增入口需安装ABI7主包，历史CLI和已开工旧任务保留原收据，不得伪造先审后规划的历史或重开最终报告。详见[完整流程与恢复](../docs/guides/flow-recovery.md)。
