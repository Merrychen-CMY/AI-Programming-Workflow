# 嵌入式C规范：接入L1与DOT

采用仓库修订的《嵌入式C项目通用开发规范与工作流程》**V1.3**，以用户提供的华为**DKBA 2826-2011.5**替换原编码参考。来源条款与项目差异见 [参考采用说明](v1.3/reference-adoption.md)。它是嵌入式C项目的编码、测试和交付要求，不改变“L1生成并代理批准需求/计划、GPT/DOT推进、用户只审核L1最终报告”的主流程。机器契约结构版本仍为 **1.1**，不要与规范1.3或工作流版本混用。

## 用户与内部职责

| 阶段 | 谁做什么 | 产物 |
| --- | --- | --- |
| 需求整理 | L1记录采用规范、产品行为、指标、允许范围及项目特定限制；关键行为或设备条件不清才询问用户 | 原有统一需求文档，增加规范引用即可 |
| 接手规划 | DOT读取项目CONTRIBUTING、现有配置与源码状态；确定R0～R3、迁移边界、工具版本、权限和预算 | 内部project-profile、dev-task或等价记录 |
| 验证设计 | L1内部L1-V与DOT协调，将产品AC与适用规范规则映射到独立判据、用例和必要审查 | 内部test-plan，用户不必再审第二份文档 |
| 编码 | L3遵守风格、契约、可读性、资源/时序等要求，同步注释和测试 | 范围内代码、自测、变动清单 |
| 独立验证 | L4检查实际C实现、审查记录和最终候选证据；实际需要时执行HIL/长期检查 | 真实逐项结果及证据 |
| 失败回流 | 所有发现先交DOT分析根因，再派开发、计划或设施职责；产品AC变化交L1 | 处置、独立重验及关单记录 |
| 交付 | DOT汇总规范与产品AC覆盖、最终版本、限制及恢复方法，核对交付授权 | 用户可读结果，内部delivery-report |

33条规则的职责、适用范围和正文路径见 [结构化映射](../../policy/embedded-c.json)。规则编号帮助分诊，但不能只凭编号直接派修；例如检查器报错不一定是代码缺陷。

## 必须正确理解的要求

- 自有C代码采用华为参考及明确项目适配：每级4空格、项目默认80列目标、控制语句加花括号、禁止goto；保留平台API和错误码。SDK保持上游规范，生成文件改生成源，AI写的普通源码不属于生成代码豁免。
- 公共API用Doxygen明确参数、单位、失败状态、并发、阻塞、所有权和生命周期。不要只补空注释骨架。
- 可读性审查关注业务主线、条件含义、查询副作用和真实职责拆分。嵌套超过3层、条件超过3个原子判断或混用与/或触发项目评审；新增函数还须满足50个非空非纯注释行、4层嵌套的规则，超出应整改或取得明确例外，不能仅写保留理由。避免机械拆分。
- 声称行为不变的实现重构仍按影响归R1/R2；核对路由、返回值、短路求值、MMIO读取、临界区、资源清理和时序。不能仅凭编译成功或另一份模型通过证明正确。
- 按影响选择quick/full/hil/soak；不是每个小任务都跑全部项目。必需项没执行、证据缺失或实机条件不足时如实阻断，不得以低风险为由写通过。
- 最终源码含未提交/未跟踪变动，配置、工具链、固件、设备及证据要关联。修改后重跑受影响检查；FINAL/CLOSED不是ACCEPTED，ACCEPTED也不是已获部署授权或已交付。

## 范围和例外

本规范适用于嵌入式C项目中自有及AI编写纳入维护的代码，及其适用开发流程；不把C缩进或头文件规则套到Python、网页和纯文档。新代码遵守，旧代码按已批准迁移范围推进，不顺手全仓格式化或重构。

原附录D“旧源码仅补注释”属于原ESP32项目阶段约束，**不自动成为其他项目默认限制**；若当前项目已有此限制则必须保留。设备引脚、SPI、DMA、增益、阈值和校准来自实际项目，不从原案例猜测。

MUST必须满足；SHOULD偏离需说明；MAY按需。例外记录规则ID、范围、理由、替代证据、确认依据和复核条件；交DOT按真实权限处理，不能把新增问题加入历史豁免。委托内需求/AC修订由L1独立审查后重新批准，不降低用户目标；超出授权范围则提交未完成报告，不增加中途用户审批关卡。
