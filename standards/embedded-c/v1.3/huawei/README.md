# 华为条款覆盖：Agent使用说明

本清单是仓库V1.3规范的**规范性补充**。原33个项目规则仍用于分类和回流；本清单把华为参考拆成独立、可追踪的要求，不能只用33个汇总编号代替逐条适用性判断。

从 [覆盖总览](coverage.md) 进入，或由Agent读取 [coverage.json](coverage.json) 后按章节/条款选择。JSON为权威内容，16份分章文件和总览由它生成。正文、项目差异和清单一起执行；有冲突交DOT/L2处理，不能自行择松。

## 覆盖范围与含义

用户提供的DKBA 2826-2011.5，第1—15章共139条编号项：21原则、68规则、50建议。第0.2—0.4节另拆为6项治理补充，总计145项。第0章补充ID由本仓库定义，不冒充原文编号。PDF起始页和来源指纹见 [来源清点](source-inventory.json) 与 [SOURCE.json](../SOURCE.json)。

前言、目录、人员表不是独立编码要求；第16章及延伸阅读是参考资料，不自动引入另一套规范。条款的解释、限制和例外纳入对应项目要求，示例不逐行复制，过时或不准确的泛化见 [技术说明适配](technical-notes.md)。本清单提供项目要求，不替代原文全文，也不宣称覆盖所有C语言风险或其他行业标准。

ADOPTED表示按原意纳入；ADAPTED表示有明确项目适配、强化或实现边界。所有145项均有要求、适用条件、验证方式和现有规则映射；这是**规范覆盖完整**，不是产品符合性或自动检测覆盖完整。

原则和规则对应MUST；建议为SHOULD，必须评估，偏离记录理由。少数建议依既有项目规则升为MUST，逐条写明依据。不能把“建议”视作可以直接忽略，也不能未经依据将所有建议一律强制。项目新增规则例外须经认可的权限渠道，开发者不能自行批准。

## DOT如何执行

1. L1在同一份需求中引用规范V1.3、清单revision 1、仓库commit及已有迁移边界，不让用户再填145项表格。
2. DOT首次接入时审阅145项的适用条件，建立项目适用性基线。按源码、接口、平台、构建和流程判断；尚不清楚记UNASSESSED并查证，不能默认为不适用。
3. 每次任务从基线选出通用条款与受影响条款；修改范围、平台或构建改变时复核相关适用性。无需每次重读全套，但遗漏不等于通过。
4. DOT组织L1-V将条款ID写进原任务requirements、AC、测试/审查映射；L3按条款实现和自测，L4以实际候选独立检查。格式工具无法证明命名语义、所有权、并发或性能正确，这些必须审查或测试。
5. L4/L5发现统一进入DOT/L2。代码问题分析后派L3；验证计划问题派L1-V；设施问题派L4；需求/AC变化经L1；交付目标及授权按L5或重新审批规则处理。
6. DOT交付汇总适用、已验证、未执行、失败、不适用和例外。代码或构建输入改变后使用新候选并重验受影响项，不把旧PASS或本仓库CI当作产品证据。

## 在原有记录中保存证据

无需新建一套用户审批表。项目可以在现有任务/验证记录中维护下列信息，或由内部工具生成关联记录：

| 信息 | 要求 |
| --- | --- |
| 条款ID | 使用HW-P/R/S编号或HW-G治理ID；同时保留33条项目规则分类 |
| 基线 | 规范版本、清单revision、仓库commit及产品候选/配置身份 |
| 适用性 | UNASSESSED、APPLICABLE或NOT_APPLICABLE；不适用必须有对象范围、理由和复核依据 |
| 执行结果 | 初始NOT_RUN；之后使用真实PASS、FAIL、BLOCKED、ERROR或SKIP，不适用不是PASS |
| 验证与证据 | 具体方法、命令/工具版本或审查位置、证据引用、运行/审查身份与时间 |
| 建议偏离 | 必须说明已评估及偏离原因，不是静默遗漏 |
| 规则例外 | 原条款、影响范围、风险、替代措施、证据、认可的确认者/授权引用和复核条件 |

使用原Schema时，`requirements[].requirement_id`可直接使用`HW-S-2.5`等合法ID；`source`指向该条款文件及锚点，`source_version`使用`1.3`，`verification_method`按真实方法选取。清单revision和commit以及适用性细节放等价关联记录，不向禁止额外字段的Schema中硬塞新字段。计划和报告引用同一ID；需要审查的条款也要有证据，不只是测试用例。

## 已实现的仓库检查

`python scripts/huawei_coverage.py`检查139个编号ID与6个治理ID的完整、唯一、强度、来源页、字段、规则映射和生成视图一致性。`python scripts/validate_repo.py`还检查文件链接、来源摘要及流程边界。默认CI同时运行这些检查和拒绝用例。

这些检查**不读取产品C代码、不运行产品工具链、不验证人工例外权限，也不证明所有自然语言解释正确**。PDF原文保留在用户资料中，不上传全文；来源页和说明由维护者核对。产品若没有所需检查器，应采用认可的独立审查或保持未验证，不能把尚未安装的工具写成已执行。

## 维护步骤

修改权威JSON并核对来源编号、原意、说明与例外；原文换版才更新来源指纹和清点。运行`python scripts/huawei_coverage.py --render`重建Markdown，再更新V1.3的派生哈希、根MANIFEST和相关测试。内容摘要更新不等于审批。生成视图不可单独编辑，测试必须拒绝漏项、重复、降级和虚假产品PASS。
