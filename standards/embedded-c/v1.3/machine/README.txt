嵌入式 C 开发流程 1.3 — 机器可读任务契约
规范正文版本：1.3（仓库修订，华为参考版）
JSON 字段结构版本（schema_version）：1.1
用途：为后续项目提供统一的项目配置、开发任务、测试计划和交付报告结构。

字段结构保持1.1，Schema的$id也保持不变。项目standard_version现在允许1.1、1.2、1.3，新模板使用1.3。旧包拒绝1.3时应升级校验包，不能伪报版本。旧记录结构通过不证明已迁移到当前华为参考。
当前编码参考为用户提供的DKBA 2826-2011.5；采用规则和项目差异见../reference-adoption.md。只增加正文支持版本，没有部署代码格式、复杂度或全部规则检查器。

一、交付内容与边界

project-profile.template.json   项目长期复用的范围、工具、设备、授权、日志与检查配置。
dev-task.template.json          单次开发的目标、范围、不变行为、需求、验收和预算。
test-plan.template.json         已确定的测试集合、判据、命令、设备前提和证据要求。
delivery-report.template.json   最终版本身份、执行结果、变动清单和验收结论。
四份同名前缀的 .schema.json     对应结构、必填字段和状态条件检查。
common.schema.json             共用字段定义。
tools/validate_contracts.py     仅校验契约结构的只读入口。
tools/requirements-validation.txt  本校验入口的固定 Python 依赖。
tests/test_contract_schemas.py  可复跑的 44 项契约 Schema 自检。
tests/test_contract_validator.py  可复跑的 23 项只读校验入口回归。
tests/test_readability_contracts.py  可复跑的版本兼容及可读性契约补充检查。

这四份模板都处于 DRAFT。null、空数组、零预算是“尚未配置”，不是默认授权，
也不是完成或通过。没有填入任何项目命令、真实设备、产品测试结果或固件。
本包不包含通用测试执行器，不会打开串口、构建产品、烧录、复位或修改产品工程。
Schema 校验通过只说明文档结构及部分条件合法，不能证明测试真的执行或产品正确。

二、启用顺序

1. 复制模板到项目约定的流程目录；不要直接把模板本身当作已执行记录。
2. 先填写 project-profile：规范版本、自有/第三方/生成源码范围、固定工具版本、
   quick/full/hil/soak 的入口或不适用理由、设备稳定身份、既有授权和资源预算。
3. 每项工作建立 dev-task。填写需求、允许修改范围、不变行为、风险、验收判据、
   授权引用和测试计划路径。小任务由 AI 复用项目配置并填必要内容，不要求用户
   手工填写每个技术字段。影响验收或行为的未决事项清除后才可 READY。
4. 建立 test-plan。将需求、验收条件与具体 test_id 对应；在写实现前确定关键
   判据来源。逐样本算法测试应调用实际 C 实现，硬件/时钟/资源依赖按需替换。
5. 执行本地 Schema 校验，再完成本说明“跨文件与运行期语义检查”。两者通过、
   必要授权与前提仍然有效时，可以转 READY；READY 不等于允许任意硬件操作。
6. 执行时转 ACTIVE，受现有授权范围和总预算约束；人工步骤未完成时阻塞依赖
   操作，不能把等待时间当作授权或人工完成的证明。
7. 交付报告默认 INCOMPLETE。执行结束后绑定最终源码/配置/参数/固件和证据，
   给出 ACCEPTED、INCOMPLETE 或 REJECTED。FINAL 表示报告已定稿，不表示通过。
8. CLOSED 仅表示任务/计划执行流程结束；实际验收状态仍以交付报告为准。
   授权或范围变化要更新对应记录；仍有效的预授权不需要每一步重新询问。

三、固定枚举与语义

规则强度：MUST / SHOULD / MAY（见主规范）。
风险：R0 注释与文档；R1 普通行为；R2 驱动、并发、资源、算法、参数或标定；
      R3 发布或安全敏感。根据实际影响升级，不得为了少测擅自降级。
开发模式：COMMENT_ONLY / FORMAT_ONLY / FUNCTIONAL / RELEASE。
COMMENT_ONLY 只允许 COMMENT、DOCUMENTATION 类变动；新增产品逻辑、调整配置、
算法参数或顺手重构均不属于此模式。必要验证工具可另列独立授权任务。
项目/任务/计划状态：DRAFT / READY / ACTIVE / CLOSED。
报告状态：DRAFT / FINAL。
单项结果：PASS / FAIL / SKIP / BLOCKED / ERROR / NOT_RUN。
适用性：APPLICABLE / NOT_APPLICABLE，独立于测试结果。
NOT_APPLICABLE 必须有事前范围判断依据和理由，记录结果为 SKIP。
NOT_RUN 是尚未运行；BLOCKED 是因明确前提不满足而无法运行；ERROR 是执行器、
测试环境或结果解析异常。真实断言失败为 FAIL，不能改写成 SKIP。
验收：ACCEPTED / INCOMPLETE / REJECTED。
必需且适用的测试 SKIP/BLOCKED/NOT_RUN，验收不能完成；实际行为不满足判据时
不能接受。环境或执行器错误未排除时也不能接受。具体失败原因必须保留。

日志等级：ERROR / WARN / INFO / DEBUG / TRACE。使用不同平台等级时，在项目
适配层明确映射，例如 TRACE 对应某平台 VERBOSE，禁止仅因名称不同丢失语义。
模块、事件编号、事件发生时间、启动/运行身份、限流和丢弃策略由项目配置约定。
日志不得包含密钥、密码或未经约定的敏感信息；环境配置仅引用名称，不写凭据。

四、字段填写要点

1. requirement_id / criterion_id / test_id / assertion_id / artifact_id：
   使用稳定、唯一的 ID，例如 REQ-WEIGH-001；不要把数组下标当永久身份。
2. oracle：写明需求、手册、独立参考、已确认测量或复核数据集的出处和版本。
   不允许直接以待测实现计算的输出作为唯一正确性判据。
3. command.argv：实际程序与参数列表，不使用依赖隐式 shell 解析的命令字符串。
   working_directory、environment_profile、expected_tool_version 必须明确。
4. source_manifest：记录最终参与构建/检查的实际文件及哈希，覆盖未提交修改
   和未跟踪源码。只有 Git revision 或“工作区干净”声明都不够。
5. artifact.path：可以是归档内相对路径或受控存储 URI；sha256 必须由真实文件
   计算。不能为了通过 Schema 填入占位哈希。
6. test_kind=HOST_BEHAVIOR：必须验证真实 C 实现；Python 可以负责调度、生成
   输入和独立判据，但仅测试另一份 Python 算法不能替代固件逻辑回归。
7. execution_environment=DEVICE：必须关联稳定设备身份、独占访问和授权；
   COM 号等运行期端口仅为发现结果。HIL 固定使用 DEVICE，SOAK 可用于主机或设备。
8. retry_policy：只允许已说明的临时基础设施故障重试，保留每次尝试和原始证据。
   不因重试、部分进展或人工等待无限重置总预算；修复后重新验证另记一次运行。
9. device_observations：记录运行/固件身份、供电复位历史、人工动作和波形状态。
   “波形未实测”必须明确，不能用日志成功代替电气验收。
10. firmware_applicability：纯文档任务可以 NOT_APPLICABLE 并给出理由；涉及
    实际固件验证则必须绑定固件。不能用这个字段绕过计划要求的构建或烧录验证。

五、Schema 能检查的内容

本包使用 JSON Schema Draft 2020-12，可检查必填/未知字段、类型、枚举、哈希
格式、时间格式（校验器需开启 format 检查）、部分激活条件、只补注释的变动
类别、真实 C 测试声明、设备测试的设备/授权引用，以及 ACCEPTED 的必要条件。
空模板直接修改 status=READY，或将空报告标为 ACCEPTED，均应失败。
ACCEPTED 禁止零发现、零执行、缺少必需项、未完成必需项或失败/错误/阻塞结果。
本包提供的 DRAFT 模板不包含任何真实执行结果；Schema QA 只测试契约自身。

Schema 的 $id 使用保留的 .invalid 域名，仅作为标识，不是下载地址。
加载时将同目录五份 Schema 按各自 $id 注册到本地解析器，使用本地资源解析
common.schema.json；不要尝试联网下载这些标识。模板 schema_ref 指向同目录文件。
jsonschema 的 Draft202012Validator + 本地 referencing.Registry 是一种实现方式；
也可以使用兼容 Draft 2020-12 的其他校验器，必须验证引用和条件规则生效。

六、必须由项目检查入口追加的语义检查

以下内容不能靠 JSON Schema 或 AI 的布尔声明证明；项目执行器/验收程序必须
计算并核对，不能把 JSON 填成 true 就放行：

A. ID 唯一；跨文件 project/task/requirement/criterion/test/assertion/artifact/
   device/grant 引用全部存在；任务需求与测试覆盖一致，无孤立或遗漏必需条件。
B. 测试集合来自已确定的计划与项目风险规则。禁止通过删除用例、改 required、
   改适用性、放宽容差、关闭检查或降低风险得到通过；变动需依据及审查记录。
C. quick/full/hil/soak 的选取与变更影响一致；不能凭名称宣称覆盖了全部测试。
D. 实际框架发现的测试与计划选择一致，零发现或缺失必需测试是异常。
   discovered 是执行器/框架实际识别的唯一测试项（含正式登记的人工验证项），
   不是任务文件里填了几项就算发现。每个底层测试程序返回 0 但没有预期测试
   结果时仍不能通过；不能仅验证上层脚本退出码。
E. 汇总计数从单项结果和实际尝试计算；各项互不重复，测试 ID/断言集合完整。
   executed 仅统计真正开始执行的唯一测试，不能将 NOT_RUN、未执行的 BLOCKED
   或仅登记的人工项计入。重试次数不增加 discovered/唯一测试数。
F. 开始/结束时间、尝试序号、最终结果与原始证据一致；先失败后通过不能抹去
   先前失败。断言失败、构建失败或执行超时不能被包装成环境跳过。
G. 所有 artifact 文件实际存在、哈希匹配、来源和访问权限正确；证据与最终
   源码、配置、参数、工具链、固件相符。最后一次受影响修改之后必须重测。
H. 开发前 planned_source/starting_source 用于说明起点；交付证据必须绑定
   final_identity，不能要求开发前后源码哈希相等，也不能用起点代替最终版本。
I. 有设备验证时核对设备稳定身份与固件身份，检查独占锁、运行期前提和授权范围。
   无授权、设备不匹配、前提未知或预算耗尽时不得执行依赖操作。
J. 预算同时受项目默认、任务和单项限制；取得部分进展不自动延长总预算。
   等待人工动作不等于动作已完成。不可恢复时记录状态并按已定义方式安全结束。
K. 参数/校准和诊断/正式配置差异已记录；旧参数适用性、缓存残片、采集间隙、
   复位及数据过期均有明确处理。实物、波形、时序等未验证事项不能自动判为通过。
L. 非适用和可选未执行项的理由已审查且不影响验收；失败项不能由简单汇总忽略。
   只补注释时另行验证非注释代码与必要的预处理行为未变，单靠category标签不够。

七、如何减少维护成本

项目 profile 长期复用；任务/计划由 AI 按变更填充并校验；结果与文件哈希尽量
由测试工具生成，而非人工抄写。AI 负责分析和修复，确定性的脚本负责执行判据。
先接入已有构建、测试和日志工具，再逐步增加设备夹具与长期测试，避免一开始
开发跨所有芯片和项目的通用执行器。必需检查不因自动化尚未完成而宣称通过。

八、本包验证记录

本次对四份 DRAFT 和五份 Schema 进行了实际结构校验，并用仅存在于验证程序
内存中的人工构造样例检验 READY/ACCEPTED 条件及拒绝路径。
这些人工样例只检验模板契约，未执行任何产品功能测试、回归、烧录或硬件操作。
详细校验记录由配套交付清单列出；本包不携带验证工具的第三方依赖。

九、只读契约校验入口

tools/validate_contracts.py 仅读取 JSON 与本包五份 Schema。它不启动产品命令，
不访问串口，不烧录，也不承担前述跨文件/运行期语义检查。
使用 Python >= 3.11；建议在项目独立虚拟环境按固定依赖文件安装，不修改产品
运行环境或全局 Python。依赖仅用于开发流程文件校验，不能打入固件。

在 machine 目录中的使用示例：

python -m pip install -r tools/requirements-validation.txt
python tools/validate_contracts.py dev-task.template.json test-plan.template.json
python tools/validate_contracts.py --require-ready dev-task.json test-plan.json

默认 --schema-dir 是校验脚本上两级的 machine 目录，也可显式指定包含五份
Schema 的目录。五份文件按 $id 离线注册，任何未注册引用都失败，不联网下载。
实例 schema_ref 只能为本包四份实例 Schema 的确切文件名；含目录、绝对路径、
URI、目录外跳转均拒绝。Schema 文件本身解析到指定目录之外也会拒绝。

退出码：
0  全部实例结构/部分状态条件合法，不表示允许执行或产品已通过。
1  实例 JSON、schema_ref、字段或状态条件不合法。
2  --require-ready 下，结构合法但至少一份实例仍为 DRAFT。
3  工具/用法错误，例如缺少输入、依赖缺失、文件不可读或 Schema 损坏。

多实例检查会继续检查其余文件，最终按 3 > 1 > 2 > 0 汇总退出码。
--require-ready 只额外阻止 DRAFT；READY、ACTIVE、CLOSED 或 FINAL 的实际含义
仍由对应契约决定。FINAL 且 INCOMPLETE/REJECTED 的报告结构可以合法，绝不能
因该命令返回 0 而认定验收通过。交付验收必须单独检查 acceptance_status、
实际证据及本说明第六节的语义条件。

没有实例输入时退出 3。--help 仅显示帮助；不代表运行过检查。
程序只报告结果，不静默改写实例文件。JSON 重复键和 NaN/Infinity 一律拒绝；
1e309 等超出有限浮点表示范围的数值也会拒绝，防止解析后悄悄变为无穷值。

十、校验工具自身的回归测试

安装同一份固定校验依赖后，可在 machine 目录执行：

python tests/test_contract_schemas.py
python tests/test_contract_validator.py

也可在任意工作目录使用这两份脚本的绝对路径；资料包位置由脚本自身位置推导。
两份脚本分别执行 44 项 Schema 正反例检查和 23 项 CLI 回归，成功返回 0 并输出
简洁摘要；失败返回非零并报告定位信息。所用样例只用于验证契约和检查工具，
不能当作产品功能、硬件或固件验收证据。它们不依赖制作阶段的 _qa 目录或生成脚本。

默认不在资料包中写入任何报告；CLI 测试的人工 JSON 输入仅位于系统临时目录，
退出时清理。需要保存报告时，可给任一脚本增加 --report 后跟 JSON 文件路径；
父目录需已存在，例如：

python tests/test_contract_schemas.py --report /指定已有目录/schema-tests.json

可选报告路径属于显式输出要求；未指定时不修改资料包。测试不会执行模板中
描述的产品命令，不打开串口，不操作开发板。以后修改 Schema 或校验入口时，
应复跑这两组测试，并依据新增行为增加对应用例。

十一、V1.3 可读性要求如何进入现有契约

正文第 3.1、3.2 节新增以下规则，不新增一套与任务记录脱节的审批表：

READ-001：抽象层次与业务主线。顶层能复述业务阶段及主要失败路径。
READ-002：条件表达与业务分组。判断按可命名的业务规则组织，注明数据来源。
READ-003：提前返回与清理。允许守卫式返回；取得资源后的所有路径需完成清理。
READ-004：查询与动作分离。查询无业务副作用；MMIO 等特殊读取须说明访问语义。
READ-005：命名及操作/结果语义。明确操作、受理、运行、拒绝及结果，不滥用裸数值。
READ-006：有意义辅助函数及冗余分支。避免无意义包装、重复判断和不可达分支。
READ-007：复杂度触发评审。嵌套超过 3 层、单一条件超过 3 个原子判断、混合
          &&/|| 等普通评审触发线不是机械硬限，触发后记录处置或保留理由。
          新增函数另须满足不超过 50 个非空、非纯注释物理行及 4 层嵌套；
          例外须记录并经授权评审，普通保留说明不等于例外批准。计数口径以
          正文第 3.2 节为准；不得仅移藏条件，也不自动重写历史代码。
READ-008：重构语义与时序保持。保护短路求值次序/次数、硬件读取、同步关系、
          返回值、幂等行为、路由和冲突优先级；不得借可读性重构改变业务行为。

开发任务 dev-task：

1. 在 requirements[] 中按适用范围列入 READ-001 至 READ-008，source 指向正文
   对应节，source_version 写 1.3。verification_method 使用 REVIEW 或 COMBINATION
   等实际方式；不要将所有规则机械拆成八个独立执行任务。
2. 在 objective 与 interface_state_and_data_contracts[] 中说明业务阶段、请求
   受理与实际执行的边界、判定规则及阻塞理由、状态来源、异常和资源恢复责任。
   流程较长时引用与源码同版本保存的流程草图或判定表，不复制多份契约。
3. 将必须保持的路由/返回/优先级/幂等行为、短路求值次数与顺序、寄存器访问、
   检查与提交原子性写入 scope.unchanged_behaviors[]；不要只写“功能不变”。
4. acceptance_criteria[] 分别描述可观察行为与可读性评审结果。新增函数50行/4层须满足或获准例外；普通评审触发线
   不是通过/失败的唯一依据；触发项需有定位、处置或保留理由及对应证据。
   未决定的行为或时序差异先记 open_decisions，不能擅自当作冗余删除。
5. 改控制流、调用结构、数据结构或资源处理的重构不能按 R0 或 COMMENT_ONLY
   处理。按真实影响选 R1/R2 等风险；当前只补注释阶段仍禁止顺手重构旧代码。

测试计划 test-plan：

1. cases[] 可组合 STATIC、MANUAL_REVIEW 与 HOST_BEHAVIOR 等测试：静态检查提供
   候选问题，评审检查业务主线与规则分组，行为测试调用实际 C 实现。
2. 为受影响的路由、返回码、已运行请求、冲突优先级和正常/拒绝/异常路径设置
   判据。按适用性追踪查询次序、调用次数和寄存器访问，检查提前返回及所有资源
   释放路径；并发/临界区与时序变更还需对应设备验证或明确未验证限制。
3. test_id 与 acceptance_criteria[].required_test_ids 对应，判据来源在 oracle
   中记录。不能仅用另一份重新编写的伪代码证明实现正确，也不能把“编译通过”
   当作业务流程或时序等价的证明。有限用例通过不意味着对所有输入形式化等价。
4. 若项目采用 clang-tidy 或其他复杂度工具，在 project-profile.toolchains
   固定版本/config，在检查入口记录阈值、计数口径和范围。未部署时如实采用
   MANUAL_REVIEW；本包没有安装、配置或运行项目级 clang-tidy 可读性检查。

交付报告 delivery-report：

1. change_manifest[] 说明分解后的职责及实际行为影响；test_results[] 和
   evidence_artifacts[] 绑定最终实现的评审、测试、访问轨迹或测量记录。
2. independent_review / acceptance_evidence 引用复杂度触发项的处置和行为保持
   证据；每项保留理由需对应具体代码位置，不能仅填写“已审查”。
3. limitations_and_unverified_items[] 保留不能证明的时序、硬件副作用或组合
   场景；必需项缺少证据仍为 INCOMPLETE，不可因函数变短或警告减少宣称通过。
