嵌入式 C 项目通用开发规范与工作流程 V1.2 使用说明

一、先看什么
首次使用先读第 1、2、8、11、12 节；从 V1.1 升级时重点读新增第 3.1、3.2 节和变更记录。
第 3 至 7 节是编码与工程要求，第 9 至 10 节是测试及硬件要求，附录 A 至 C 为可直接填写的表单。

二、文件分工
嵌入式C项目通用开发规范与工作流程_V1.2.docx：规范与填写表单。
规范正文检索版.txt：与 Word 同次生成、包含表格的检索副本，便于 AI 读取；不要独立维护。
rules-index.json：33 项关键规则的索引、范围与检查方式；详细规则以正文为准。
项目规范入口模板.txt：供项目 CONTRIBUTING.md 引用规范及真实配置。
AI项目指令模板.txt：供项目 AI 指令引用已有入口，不重复抄写完整规范。
可读性审查清单.txt：复杂流程设计、条件审查、行为保持验证及交付自查。
machine/：四份 JSON 模板、五份 Schema、字段说明、只做契约校验的工具及可复跑测试。
validation/：本资料包的校验记录；这些不是任何产品的测试或验收记录。
变更记录.txt：相对前版的变动与范围。
checksums.sha256：本包文件的一致性校验值，不代表产品验收。

三、如何开始一个新项目
1. 将本包保存到项目文档目录，采用 V1.2；合并入口模板到项目 CONTRIBUTING.md。
2. AI 根据项目已有信息填写 project-profile，用户只需补充无法确定的需求、设备或授权边界。
3. 从 dev-task 和 test-plan 建立任务与测试约定。采用一个权威数据源，避免 Word 和 JSON 重复手工填写。
4. 先做结构校验，再做 README 规定的跨文件和现场条件检查；未配置完整时保持 DRAFT。
5. 将实际构建和测试命令接入项目原有工具。先 quick/full，随后根据需要接入 hil/soak。
6. 执行后由工具生成结果及证据，AI 汇总交付报告，最终验收状态由判据和必要检查共同决定。

四、使用边界
这次完善的是规范、模板与契约校验工具，没有部署产品测试执行器、CI、自动烧录或夹具。
模板不含真实命令、设备、固件或有效校准，不得把空值和占位内容作为默认生产参数。
结构校验通过不表示允许执行硬件操作，也不能证明记录中的哈希、授权或测试结果真实。
机器模板的使用和校验命令见 machine/README.txt；所有待填写项须按项目实际情况处理。
规范版本 1.2 与结构版本 1.1 独立：字段未变化，不需迁移任务 JSON 结构；项目采用版本需明确。
复杂度阈值是评审触发线，工具只能辅助识别；不得把模板交付视为已自动评定可读性。

五、维护方式
规范修订时同步更新版本、检索副本、规则索引、相关模板和变更记录。
项目硬件参数只放项目配置，本次任务验收条件只放任务/计划；通过引用关联，不在各处重复抄写。
第三方依赖仅用于校验工具，不纳入固件。当前工程“仅补注释”限制不应自动套用到其他项目。
