# 3 编码风格与头文件

规则 C-001、HEADER-001。自有 C 源码参考 Linux 内核风格，固定格式化工具版本及配置；项目明确采用以下例外：禁止 goto、控制语句统一加花括号、使用 Doxygen。

编码要求

使用 Tab 缩进，显示宽度为 8。以 80 列为可读性目标，必要时允许合理超出。函数左花括号另起一行，控制语句左花括号放同行。

函数与变量采用清晰的下划线命名，常量宏及枚举值采用大写。结合上下文命名，不机械禁止 i、j 等局部索引。

函数职责单一，控制嵌套深度。避免隐藏控制流或具有难以发现副作用的宏；注意宏参数重复求值。

禁止使用 goto，包括错误清理。通过辅助函数、分阶段初始化及明确资源所有者处理清理，避免以多层嵌套替代清晰控制流。

保留平台规定的类型、API 和错误码。不照搬内核专用接口，不因风格统一而改动 SDK。

检查整数溢出、符号转换、截断、浮点非有限值及时间计数回绕。单位、取值范围和精度在接口边界明确。

头文件要求

每个头文件使用 include guard，名称包含项目、模块和文件名，全大写且不以下划线开头。守卫名称在项目中唯一。

头文件必须自包含；普通函数实现和具有存储空间的变量定义放在 .c。允许必要的类型、常量宏和经审查的 static inline。

有对应头文件的 .c 优先包含自己的头文件。跨模块调用包含对方公共头文件，禁止手写对方函数声明。

避免暴露可变全局变量和私有结构；接口只公开调用者确实需要知道的类型与约束。不为没有公共接口的源文件机械创建头文件。

迁移与变更纪律

新代码遵守本规范。旧代码按项目迁移计划逐步处理，独立格式整理、批量注释和功能修改分别提交；与功能直接相关的注释和测试随功能一起提交。检查默认报告问题，不静默重写代码。

当前 ESP32 项目的“旧代码只补注释”限制见附录 D，属于阶段约束。通用规范不永久禁止后续经授权的功能开发或缺陷修复。任何源码、配置、构建、测试及生成源变动都进入变动清单。
